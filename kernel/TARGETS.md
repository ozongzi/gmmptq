## 已否证：沿 K 切分并跨核归约（对点 13）

截至 2026-11-08 已测约 32 个变体。**每一个「在固定的工作划分内重排」的办法都失败了**：
tile 几何、路径选择、DMA 描述符形状、DMA 发射顺序、cache 预读、双缓冲、删死代码。

事后看这是**一个结果而不是八个**——它们都没有改变「工作总量除以核数」这件事。

| 点 | 每核工作单元 | 评测比值 |
| --- | --- | --- |
| 2 | 1.0 个 tile | 1.46–1.79 |
| 11 | 1 个 batch（40 个 block 里 38 个） | ~1.30 |

**唯一能创造更多工作单元的办法是沿归约维度 K 切分、再跨核归约**：点 2 的 K=511 切 4 份得 4 倍单元，

本身有流量和同步代价——但它是唯一量级对得上的方向，而且**三个点是同一个机制，一份实现可以服务三处**。

从点 13 入手：它纯 AIV（无 AIC/AIV 握手要重新设计）、`Row()` 已按 `kc_` 沿 k 分块（部分和结构已部分存在）、

## 已否证：每核 tile 数 → 延迟暴露 → judge/local 比值

**吞吐随时钟缩放，延迟不随。** 所以两台机器之间真正不同的是**未被流水掩盖的延迟**，
而每核 tile 数（或每核 batch 数）决定有多少延迟被暴露。

| 点 | 每核 tile | judge/local |
| --- | --- | --- |
| 2 | **1.0**（4 M-tiles × 5 N-tiles = 20 / 20 核，因 `rowsPerExpert=64 < BM=96`） | **1.79** |
| 4 | 3.5 | 1.38 |
| 1 | 6.4 | 1.28 |

单调反相关。这解释了为什么**点 2 的两条结构完全不同的路径在判题器上都落在 ~15.5 µs**：
它的耗时是纯未流水化的 per-tile 延迟，与 body 结构无关。

**这同时修正了我先前那个「被否证」的模型。** 我原本用每核 tile 数解释 `cube_mac` 吞吐，
于是预测点 4 减小 BM 会更快——测量否证了它。正确的被解释量是**延迟暴露**：
点 4 在 3.5 tiles/core 已经流水起来、是 B 流量受限，减小 BM 只会增加流量；
点 2 在 1.0 tiles/core 则完全没有可流水的东西。两件事不矛盾。

**可证伪预测**：点 2 用 `BM=32` 使每核 tile 变为 2.0，应当**本地变慢、评测变快**。
（注意 `if constexpr (BM > 32 && BM != 208)` 守卫跨核握手，BM=32 会首次走那条在所有现存实例中都是死的早握手路径；
退路是 BM=48，`ceil(64/48)=2` 仍给每专家 2 个 M-tile，而 BM=64 只给 1 个。）

### 点 13：代码级确认 —— 重叠存在但只有一级且起步太晚

`BalancedOverlapShortGroupMatmul`（`h-merge/kernel.asc:1320`，1632 行以 `Static=true` 实例化）。

chunk `i+1` 的 weight DMA **确实**在 chunk `i` 的向量工作完成前发出，**但不是双缓冲，且被 chunk i 的前三分之一工作卡住**：

```
Row():       Duplicate(acc_,0); PipeBarrier<PIPE_V>();
             IssueInputs(..., k0=0, ...);            // chunk 0
             for (k0=0; k0<k; k0+=kc_) LoadChunk(...);

LoadChunk(): WaitFlag<MTE2_V>(0); WaitFlag<MTE2_V>(1);
             Cast(xh_,xr); Cast(wh_,wr);             // 把 raw 腾空
             PipeBarrier<PIPE_V>();                  // 完整 V 流水排空
             SetFlag<V_MTE2>(0); SetFlag<V_MTE2>(1);
             if (k0+kc_<k) IssueInputs(..., k0+kc_, ...);   // chunk i+1 在这里才发出
             Cast(xf_,xh_); Cast(wf_,wh_); ... MAC
```

只有**一对** raw 落地缓冲（`xraw_`/`wraw_`），`IssueInputs` 复用它们并必须先 `WaitFlag<V_MTE2>`。所以：

- chunk `i+1` 的 DMA 只与 chunk `i` 的**尾部**重叠（两个 f32 `Cast`、`Brcb`、MAC 累加）
- 它必须等 chunk `i` 的前导 half `Cast` 对**加一个完整 `PipeBarrier<PIPE_V>`** 完成才能发出
- **每个 `Row()` 的 chunk 0 完全没有重叠**，而它前面的 `Duplicate(acc_,0)` + `PipeBarrier` 是纯串行头部时间，本可藏在那次 DMA 下面

点 13 的几何让这个未重叠的头部成为主导：`cols = min(nPitch,192) = 192 < n = 257` ⇒ 每行需 2 个列 tile，
`k=255` 配 `kc_=128` ⇒ 2 个 k-chunk，于是 `63 专家 × 1 行 × 2 列 tile = 126 次 Row()` 分到 40 核 ≈ **每核 3.2 次**，
每次都付一次完整暴露的 DMA 延迟加一次 V 流水排空才能请求它的第二个 chunk。
**这与 E4 的结果一致——若阻塞是依赖而非传输，描述符形状当然无关。**

两个改动（已批准）：

1. **免费、零风险**：把 `IssueInputs(k0=0)` 挪到 `Duplicate(acc_,0)`+`PipeBarrier` **之前**，让累加器清零藏在 chunk 0 的 DMA 下。`acc_` 与 `xraw_`/`wraw_` 不相交，且进入时 `V_MTE2` 标志已由上一次 `Row()` 的末次 `LoadChunk` 置好。
2. **真正的修法**：按 chunk 奇偶真正双缓冲 `xraw_`/`wraw_`，使 chunk `i+1` 的 DMA 在 chunk `i` 的前导 `Cast` 对**之前**就发出，彻底把 `V_MTE2` 依赖从发射路径上移除。代价是多一对 raw：`kc*pitch + kc`。在 `kc=64, nb=192` 下 UB 为 `10336 + 448 + 86016 + 2880 = 99,680`，加 `64*192+64 = 12,352` 约 112 KB，对 188,160 很宽裕。而且**两个改动互相增强**：`kc` 减半把每个 `Row()` 的 chunk 数从 2 提到 4，同时抬高了处于重叠区的比例。
   注意设备侧 `while (kc_*pitch > capacity_) kc_ /= 2` 会独立重算 `kc_`，**奇偶索引必须按设备的 `kc_` 而非 host 的 `t_->kc`**，否则两个槽会失步。

### 实验设计缺陷：C2/C3/C5 曾被 C3 污染

C1–C5 那个阶梯是**累积**的，而 **C1 被放在了底座**。既然 C1 单独就崩，那么 b（C1+C3）、
c（+C2）、d（+C5）三级的崩溃**全部只能归因于 C1**——C2、C3、C5 本身一次都没被真正测过。
唯一通过的 `h-p11e`（+C4）被判断为「C4 恰好掩盖了 C1 的问题」，即它是潜伏 bug 而非修复。

**所以「序章重排对点 11 无效」这个结论不成立。** 必须去掉 C1 重做：

| 变体 | 内容 |
| --- | --- |
| `h-p11B2` | C3 单独（groupList 改为一次 DMA 进 UB，替掉四次冷标量 `GetValue`） |
| `h-p11C2` | C3 + C2（序章重排：预读 + x 的 DMA 投机提前 + weight 往返与 `ws` 读下移） |
| `h-p11D2` | + C5（把 `weightScale` 折进 `scales`） |
| `h-p11E2` | + C4（用 `dstRepStride=1` 的二级归约消掉 `Gather`/`CreateVecIndex`；H6 已查证合法） |

教训：**阶梯式累积实验里，任何一级崩掉就污染它之后的全部结论。** 底座必须是最保守的改动，
或者各改动单独成变体而非累积。

### 下一轮主线：单核内的软件流水（双缓冲）

两次失败里浮现出同一个形状，它不是「搬得太多」也不是「算得太慢」：

- **点 11**：40 个 block 里 38 个各跑一个 batch 就退出（`1027/40 = 25.7 < R = 32`），没有第二份工作可掩盖延迟。
  时间账：启动 1.10 + DMA 1.26 + 向量 0.4 = 2.76 µs，实测 7.05 ⇒ **缺口 4.3 µs 是裸露的 DMA 延迟**
- **点 13**：63 个专家 / 40 核，每核串行流约 `2 × 65,535` 字节，**每核仅 6.7 GB/s**

**双缓冲的 UB 账是免费的。** 点 11 现在 `xl`/`even`/`odd`/`f`/`other` 合计 `7·R·C`；
把 `R=32` 单缓冲换成 `2 × 16` 双缓冲，总量 `7·(2·16)·C` **完全不变**，只是切成两半。
每核 `nr ≤ 26`，可切成 16+10 或 13+13。一边算一边取下一批，**不花额外 UB**。

同一手法用于点 13 的 weight 流：`Row()` 在设备侧重算 `kc_`，所以 chunk 边界本就在那里，
问题只是 chunk `i+1` 的 DMA 是否在 chunk `i` 的向量工作完成前发出。

| 128 | 13 | 5.8 MB | 21.0 |
| 192 | 10 | 4.5 MB | **19.3** |
| 224 | 9 | 4.0 MB | 20.8（tile 粒度变差：63 tile / 20 核 = 3.15，行利用率 45%） |

点 4 在 `BM=192` 的总流量约 `4.5 B + 0.53 x + 1.58 y + 2.4 staging写 + 2.4 staging读 = 11.4 MB`，
`11.4 / 18.16 µs = 628 GB/s`——**已在实证上限 634 GB/s 上**。

**但「多槽 B 缓存」这条路也堵死：每核只分到 3.5 个 tile，而一个 mIdx 的 N 扫描有 7 个 tile，
单核根本看不到同一个 `nIdx` 两次，所以加缓存槽没有可复用性。** 重算 A/B 权衡：
B 流量 ≈ `M-tiles × N × kp`（与 BN 无关），要降只能减少 M-tiles；而 N-major 把 A 从 0.98 MB 抬到 6.9 MB，净亏。
所以 `BM=192` 确实接近这个算法的结构极限，与测量一致。

### 剩下的大头：staging 往返，以及它为什么难动

点 4 的 11.4 MB 里 staging 占 **4.8 MB（42%）**。但它已经是半精度 staging（2 B/元素），
即每个输出元素 `2 写 + 2 读 + 2 写y = 6 B`，而理论下限（只写 y）是 2 B。

**结构性原因**：cube 在 L0C 产出结果，而 per-token 的 `xs[m]` 只有 AIV 能施加，AIV 读不到 L0C，
所以必须经 GM 往返。Fixpipe 能施加 N 方向的 per-channel `ws[n]`（ScalarHalf 路径已在用 `DEQF16`），
但 M 方向的 per-row `xs[m]` 不行。把 `xs` 折进 `x` 也不行——`x` 是 int8 而 `xs` 是 float。

所以 6 B/元素 在当前算法下不可约。**要动它需要架构级改动，不是参数。**

## 逐点瓶颈性质

### 点 11（+54.9，最大靶子）—— 未被掩盖的串行延迟，占 58–68%

**已完成代码级诊断，结论明确。** 内核是 `SearchN1FixedLayoutSafe7100000<bf16,bf16,R=32,C=800>`
（`kernel.asc:1145..1229`），40 blocks。

**被否证的假设**：它并非每行发一次小 DMA。x 早就是**一次** `DataCopyPad`（1194 行，`blockCount=nr`、
`blockLen=769`、**`srcStride=0`**），行在 GM 里本就连续。而且**摊平成单次宽 DMA 不可表达**：
769 字节的 pitch 不是 32 的倍数，而下游每个 repeat stride 都按 32 字节块编码
（`BinaryRepeatParams row{1,1,1,width/32,width/32,0}`、`srcRepStride = pairs/8 = 50`），
摊平会让每行退化成 `repeat=1`，26 条指令取代现在的 1 条。非对齐只浪费 832/19994 = **4%**。

**真实时间去向**：

| 项 | µs | 占比 | 依据 |
| --- | --- | --- | --- |
| 40-block 启动地板 | 1.10 | 15% | 第零节实测表 |
| `TPipe` 构造/析构 | 0.31 | 4% | 第一节实测 |
| 向量发射 | 0.6–1.0 | 8–13% | 约 295 KB 发射量、1150 repeats、256 B/cycle @1.8 GHz |
| DMA 传输 | 0.35–0.7 | 5–10% | 每核约 20 KB |
| **未掩盖的串行延迟** | **4.3–5.0** | **58–68%** | 残差 |

**成因**：

1. `begin = M*blockIdx/cores`（1175）是连续分块，而 `1027/40 = 25.7` ⇒ 最大 `nr = 26 < R = 32`。
   `for(m=first;m<last;m+=R)`（1192）对 **40 个 block 中的 38 个只跑一轮就退出**——没有第二批可供流水掩盖。
   （只有 block 0 和 19 因专家边界落在第 1 行和第 512 行而跑两批。）UB 为之设计的 32 行批处理**从未被填满**。
2. **全内核没有任何 `DataCachePreload`**，而直系兄弟 `BudgetStridedRowTiny`（1100-1108）与
   `TinyCacheReduction`（1256-1275）都有。
3. `weightScale` 的标量 GM 解引用（1190-1191）夹在 `GvBarrier<V_MTE2>`（1188）与 x 的 DMA（1194）之间，
   把一个完整的标量 HBM 往返**串在最大那次传输前面**。
4. weight 的 MTE2→V→MTE2 完整往返（1183-1188）在 x 的 DMA **之前**发出，而 x 大 26 倍、
   且 weight 直到 1204 行才用到。
5. x 的 DMA 地址只依赖 `blockIdx`（1175），**不依赖 groupList**，却被排在 groupList 扫描、
   weight 往返、`ws` 读取之后。
6. 40 个 block 各自跑完整的 `for(e=0;e<s.e;++e)` 调 `gg.GetValue(e)`（1179），
   即 160 次对同一条 32 字节 cache line 的冷标量 GM 读。
7. **30 条向量指令配 19 个硬同步**（10 个 `PipeBarrier<PIPE_V>` + 4 个 `GvBarrier` + 序章 5 个）。
   尾部 1217→1222 是 5 个只处理 ≤26 元素的操作，之间夹着 5 次完整 V 流水排空。
8. **`TPipe pipe;`（1153）声明了但 `InitBuffer` 从未被调用**——每个 buffer 都是手工摆放的
   `LocalTensor(TPosition::VECCALC, offset, len)`。这个 `TPipe` 纯粹白付 0.31 µs。

**UB 余量**：布局恰好 184672 字节 / 上限 188160 ⇒ **空余 3488 字节**。
`static_assert(C%32==0 && R==32)`（1149）与 `static_assert(UB_BYTES==184672u)`（1152）都会硬失败，
且后者比的是字面量，**所以不要改 `R` 或 `C`**——也没有收益，`R=32` 本就填不满，
`C=800 = Up(769,32)` 由闸门 P 的 `K<=800` 决定。

**不要做的事**：摊平 x 的 DMA（不可表达）；改 `R`/`C`；换数值方案（pair-split 与 `i8→f16→f32`
发射量相同，各约 13–14 B/元素，而 f16 路线丢精度：`127*127 = 16129` 需 14 位尾数）；
借 `RowDot` 的 weight-scale 路径（它用一次 DMA 加 `V_S`/`S_V` 往返换一次标量加载，更差）。
`RowDot` 唯一值得借的是它的 groupList DMA（1414-1415、1418）。

**改动阶梯**（预估合计 −2.2 到 −3.5 µs ⇒ 3.9–5.2 µs 对比 tbest 5.948，即点 11 从 45 分到 95–100 分，
**总分 +3.3 到 +3.7**）：C1 去掉未使用的 `TPipe`；C3 groupList 改为一次 DMA 进 UB；
C2 序章重排（预读 + x 的 DMA 提前投机发出 + weight 往返与 `ws` 读下移）；C5 把 `weightScale`
折进 `scales`；C4 用 `dstRepStride=1` 的二级归约消掉 `Gather`/`CreateVecIndex`（**风险**，撞 H6 雷区）。

C2 有个会静默出错的陷阱：`wl` 每个专家重新 DMA 一次，而向量单元仍在读 `weven`/`wodd`，
重排后必须在**第二个**专家的 weight DMA 前保留 `V_MTE2` 栅栏（现在 1224 行只管 x）。
弄错只会让**第 0 行和第 512 行**（即 block 0 和 19）算错，粗略检查发现不了。

### 点 11 的旧分析（保留作对照）
E4 M1027 K769 **N1**，counts `[1,511,0,515]`。走闸门 P → `SearchN1FixedLayoutSafe7100000<bf16,bf16,R=32,C=800>`，40 blocks。

- 真实工作量：`1027 × 769` = 790 K MAC，微不足道
- 数据量：x 读 790 KB（每行各读一次），weight 仅 3 个非空专家 × 769 × 1 = 2.3 KB，y 2 KB
- tbest 5.948 µs ⇒ 790 KB / 5.948 µs = **133 GB/s**，远低于 HBM 能力

**所以连 tbest 都不是带宽受限的，是每行的归约开销受限。** 40 blocks × R=32 行 = 1280 ≥ 1027，整个问题一趟过完，每 block 约 26 行。每行 769 个 int8 要走 int8 配对拆分 → int16 乘积 → 两级 `WholeReduceSum`。粗估向量指令数每 block 约 768 条，按 1.8 GHz 单发射只需 0.43 µs，而实际 9.75 µs 是它的 22 倍——**时间花在 DMA 延迟、标量开销和栅栏上，不在算术也不在带宽上**。

攻击方向：加大每批行数（`R=32` 是模板参数，`C=800` 恰好是 `Up(769,32)`，两者都卡在 UB 固定布局 184672 B 上）；减少每行的独立 DMA 次数；把 40 个 block 的归约结构换成更少同步的形式。

### 点 13（+48.3）—— 一行 host 改动：让 weight 的 srcStride 变成 0

**根因已定位。** weight 的 DMA 在 `kernel.asc:1816-1822`，有两条路径：

```cpp
p = flat ? {1, klen*cols, 0, 0, 0}                      // 一次连续
         : {klen, cols, t_->n - cols, 0, 0};            // klen 次短传输
```

而 1754 行是 `const bool flat = false; // Host nb is Up(N,32), matching DMA padding.`
——**`flat` 被硬编码成 false，且注释的前提不成立**：host 写的是
`out.nb = std::min(nPitch, 192u)`（3032 行），对点 13 是 **192 而不是 `Up(257,32) = 288`**。

于是点 13 走第二条：`cols = 192`、**`srcStride = 257 - 192 = 65`**，即 `klen` 次各 192 字节、
每次跳 65 字节。整个专家在 GM 里是 **65,535 字节连续**，却被拆成约 512 次平均 128 字节的带 stride 短传输。
这就是 212 GB/s 的来源。

**修法不需要碰 flat 路径。** 第二条路径里只要 `cols == t_->n`，`srcStride` 就是 0，源地址即连续——
和点 11 那个被证实高效的 `{nr, 769, 0, 0, 0}` 是同一种描述符。
**绝不要打开 `flat`**：它的 `{1, klen*cols, 0, 0, 0}` 会让 UB 行距变成 257，非 32 对齐，
而 `kernel.asc:590` 记着「未对齐的向量操作数起始地址会挂死该单元」。

所以改动是一行：`out.nb = std::min(nPitch, 192u);` → `out.nb = nPitch;`

UB 账已核：`BalancedOverlapShortGroupUbBytes` 化简为 `10336 + 7*kUp + 7*kc*nb + 10*nPitch`，
现值 `kc=128, nb=192, nPitch=288` 得 **186,144**，与既有记录吻合，公式无误。
改 nb=288 后现有的 `kc /= 2` 循环自动把 kc 降到 64：`10336 + 448 + 7*64*288 + 2880 = 142,688 ≤ 188,160`，
尚有余量；`minWidth` 守卫算出 64，不会把 nb 抬回去。

结果：`cols = min(288, 257) = 257 == n` ⇒ `srcStride = 0`，每个专家的 weight 变成
**4 次连续传输、每次 64×257 = 16,448 字节**。

验证要点：`nb` 同时喂给行切分逻辑，而 `nPitch > nb` 本来就是设备侧要切行的原因，所以**必须跑完整正确性检查**。
对照实验：`nb=256`（刚好小于 N ⇒ `cols=256`、`srcStride=1`）应该仍然慢——若如此则机制确认，
而不是「nb 变大」带来的无关副作用。

### 点 13 的旧分析（保留作对照）
E128 M63 K255 N257，counts `[0,1]` 重复 63 次 + `[0,0]`，即 **63 个非空专家、每个恰好 1 个 token**。走闸门 S → `BalancedOverlapShortGroupMatmulKernel`（纯 AIV），40 blocks。

- weight 读取：63 × 255 × 257 = **4.13 MB**，绝对主导
- x 仅 16 KB，y 仅 32 KB，算术 4.13 M MAC
- tbest 17.617 µs ⇒ 4.18 MB / 17.617 µs = **237 GB/s**；我们估算 25.76 µs ⇒ 162 GB/s

**整场游戏就是把 4.13 MB 的 weight 流式读进来。** 注意 `K=255` 不是 32（`C0_I8`）的倍数、`N=257` 也不是——每个专家的 weight 块都非对齐，这是 DMA 效率的直接杀手。

攻击方向：weight 搬运的对齐与 burst 长度；`nb=192 < nPitch=288` 意味着设备侧必须把行切开（`BuildBalancedOverlapShortGroup` 把 `nb` 封顶 192 再抬到 `minWidth`），这个切分值得重新算。

### 点 4（+44.9，唯一有实测的大靶子）—— cube tile 行利用率仅 53%
E8 M1027 K511 N769 fp16，counts `[897,1,17,0,65,31,0,16]`。走闸门 T → `CubeFullKBodyScalarHalf<192,128,96,128>`，`Weighted=true`（`P4WeightedOwnership384`），20 blocks。

tile 账：`BN=128` ⇒ N 方向 `ceil(769/128) = 7` 个 tile。`BM=192` ⇒ 各专家 M 方向 tile 数
`ceil(897/192)=5, ceil(1/192)=1, ceil(17/192)=1, 0, ceil(65/192)=1, ceil(31/192)=1, 0, ceil(16/192)=1` = **10 个 M-tile**。

- 分配到的行数 `10 × 192 = 1920`，真实行数 1027 ⇒ **行利用率 53%**
- 总 tile 数 70 / 20 核 = 3.5，负载也不齐
- 单 token 的专家（count=1、16、17、31）各自占满一个 192 行的 tile

**但「浪费了一半算力」这个推论不成立，有个前提没验证**：Fixpipe 用的是 `mSize=mt`（tile 内实际行数，非 `BM`），所以 mmad 很可能也按实际行数发射。若如此，A 侧的行 padding 几乎不花算力，真正的代价转移到 **B（weight）的重复读取**：

- 遍历是 `mIdx = t/nTiles, nIdx = t%nTiles`，即固定 `mIdx` 走遍所有 `nIdx` ⇒ **A 驻留、B 流式**
- B 面板（`BN × kp` = 128×512 = 64 KB）每个 tile 换一次 ⇒ `70 × 64 KB = 4.5 MB`，而非空 `(专家, nIdx)` 组合只有 `6 × 7 = 42` 个即 2.7 MB ⇒ **约 1.7 倍放大**
- 专家 0 有 5 个 M-tile，它的 B 就被读 5 次

**这使 `BM` 的方向完全相反**：`BM` 越小，A padding 越少但 B 重复读越多（`BM=64` 时专家 0 变 14 个 M-tile）。两者是对立的，谁主导只能测。

（顺带：`NMajor` 分支本可让 B 驻留而流式 A，但它在全部 8 个存活实例里都是 false，是死代码。对点 4 粗算 N-major 要 `2.7 + 3.7 = 6.4 MB` 反而比现在的 `4.5 + 1.0 = 5.5 MB` 差，所以它死得有道理。）

tbest 17.004 对应 47.5 TOPS，远低于 int8 峰值，说明 tbest 也不是算力受限的。

攻击方向：**先扫 `BM`/`BN`/`BK` 实测**，用 `ab.sh` 的 sed 补丁机制，不要先猜。若证实是 B 重复读主导，方向是加大 `BM` 或给 B 做跨 M-tile 的驻留复用；若证实是 A padding 主导，方向是对小专家用更小的 tile 高度、或把多个小专家的行合并进同一个 tile。

### 点 15（+39.1）与点 14（+33.6）—— N 方向 padding + 单 token 专家
点 15：E4 M4097 K767 N1025 fp16，counts `[3073,1,0,1023]`，`BM=224 BN=128`，闸门 V.2。
- M tile：`14 + 1 + 0 + 5 = 20`，分配 `20×224 = 4480` vs 4097 ⇒ 行利用率 **91%**
- N：`ceil(1025/128) = 9`，`9×128 = 1152` vs 1025 ⇒ **89%**
- 合计约 81%。主要浪费在 **N=1025 多出那 1 列逼出整个第 9 个 tile**，以及 1 token 的专家独占一个 224 行 tile

点 14：E7 M3073 K1023 N1025 bf16，counts `[383,385,511,0,769,1,1024]`，同样 `224,128`。
- M tile：`2+2+3+0+4+1+5 = 17`，分配 3808 vs 3073 ⇒ **81%**
- N 同样 89% ⇒ 合计 **72%**，比点 15 更差

两点都带 `packWeights`（`n % 32 != 0` 命中），额外分配 `e·k·UpH(n,128)` 的 packedWeight（点 14 为 8.2 MB、点 15 为 3.5 MB）并多一道 pack。**规则 2 之 12 禁止「一次计算通过多次 kernel 完成」——`PackActiveWeightRowsInline` 若是独立 launch 必须合并，这同时也是一笔性能开销。**

攻击方向：`N=1025` 这种「超出一个 tile 一点点」的形状需要不等宽的 N tile；小专家的 tile 高度；pack 与矩阵乘融合。

### 点 2（+31.4）—— 实测 11.931 vs tbest 9.910
E4 M257 K511 N513 bf16，counts `[63,65,64,65]`。走闸门 X → `mix11` → `SearchP2Mix115300000`（`MIX_AIC_1_1`，`96,128,512,48`）。
- `rowsPerExpert = 64 < 96 = BM` ⇒ 每个专家只占一个 96 行 tile，真实 64 行 ⇒ 行利用率 `257/(4×96) = 67%`
- N：`ceil(513/128) = 5`，`5×128 = 640` vs 513 ⇒ **80%**（又是「超出一点点」）

### 点 7/8（各约 +31）—— 真实工作量，非地板
E1 M1 K8192 N2。稳态 2.04/2.07 µs，而同 block 数的 nop 地板 0.63 µs ⇒ **有 1.4 µs 真实工作量（地板占 31%）**。
这否定了 kernel 注释里「把计算全编译掉仍需 3.06 µs」那条说法。K=8192 的输入 DMA 是真活。

### 点 10（+30.4）—— store 带宽
E4 M1025 K1 **N769** fp16。`K==1` ⇒ 退化成外积，无归约。
- 输入仅约 20 KB，输出 `1025×769×2` = **1.58 MB**，每个输出一个 MAC
- tbest 6.463 µs ⇒ 244 GB/s 的 store；我们估 7.70 µs ⇒ 205 GB/s

攻击方向：纯 store 效率，`pitch = Up(N,16)`（见 `H1`，`Up(N,8)` 对 N=769 无解）。

## 共同主题

五个最大的靶子里有四个（4、14、15、2）是**同一个病**：tile 粒度与真实 token 分布不匹配，行/列利用率 53%–81%，近半算力花在 padding 上。这正是 generator 该解决的问题——按真实 `counts` 分布选 tile 几何，而不是用 `m/e` 这个均匀分布代理（`gen/CURRENT.md` 雷区 4 已记此事）。

剩下的点 11 和 13 是另一类：没有 cube 参与，瓶颈分别是每行归约开销和 weight DMA 带宽。

## 2026-11-09 用校准仪器（`judge.sh`）重测：三条否证 + 一条新线

### 点 4 的 N 尾部填充 —— 否证，且我的因果故事本身是错的

`BN` 必须是 **32 的倍数**（`ConfigureCubeFullK` 与 `CubeFullKBodyScalarHalf` 两处 `static_assert`），
所以先前设想的 112 / 80 非法。BM=192 下合法集是 {32, 64, 96, 128, 160}，真正的填尾值是
**BN=160**（5 个 tile，最后一个 129/160 = 81%）。

| 变体 | BN | RV | N-tiles | 尾部填充 | vs 基线 | cube_mac% |
| --- | --- | --- | --- | --- | --- | --- |
| 基线 | 128 | 128 | 7 | 1/128 | — | 15.0 |
| 控制（NativeM1 关） | 128 | 128 | 7 | 1/128 | −0.2% | 15.9 |
| `p4bn96` | 96 | 128 | 9 | 1/96 | **+5.6%** | 14.3 |
| `p4bn64` | 64 | 128 | 13 | 1/64 | **+13.0%** | 14.7 |
| `p4bn160n` | 160 | 112 | 5 | **129/160** | **+55.8%** | 12.3 |

**BN=128 是干净的最优点，两侧单调变差。**

**我说的「最后一个 N-tile 带 1 列有效数据占满 128 列」是错的**：`bp.dValue = nt` 且 `fp.nSize = nt`，
所以第 7 个 tile 实际只做 `Up(1,32)=32` 列的 mmad 和 1 字节宽的 B 拷贝——**硬件早就跳过了尾部**。
`N mod 128` 的相关性是真的，但因果不是这个。

BN=160 为何炸：`aicore_time` 只 +15% 而判题耗时 +56%，多出的 40% **在 aicore 忙时之外**——
staging 行从 256 字节变成 320 字节，错位毁了 GM 往返。
**规则：BN 保持 2 的幂，让 staging 行对 512 字节友好。**

附带：`NativeM1` 在点 4 上值约 0（−0.2%，噪声内），若未来需要 BN>128 可以直接去掉它
（它要求 `Up(BN,32)*kl ≤ L0B_BYTES`，在 `kl=512` 下把 BN 卡在 ≤128）。
另一个坑：`P4WeightedOwnership384::Own` 里写死了 `nt=(p.n+127u)/128u`，
即**用 BN=128 算 nTiles**，换 BN 必须同步改它，否则 host 与设备的归属划分不一致。

### cube body 加 `DataCachePreload` —— 回归，拒绝

实验设计值得复用：**8 个未被触碰的点跑的是完全相同的机器码，于是成了免费的噪声标定**。

| 组 | 均值 | 标准差 |
| --- | --- | --- |
| 8 个未触碰点（噪声对照） | −2.41% | 4.9% |
| **6 个被触碰的 cube 点** | **+2.25%** | **0.63%** |

六点全部同向（+1.5 / +3.0 / +2.4 / +1.5 / +2.2 / +2.9），离散只有对照组的八分之一 ⇒ 不是噪声。
扣掉会话偏差后预读在 cube 点上**代价约 +4.6%**。

机制：微小核里预读打断的是「标量→地址→GM 读」这条**就是关键路径**的链（值 0.09 µs）；
20-block 的 MIX cube 核序章后面紧跟一个已吃满 MTE2 的宽 `Nd2Nz`，没有链可打断，
预读只是在它前面插了五次串行标量发起的 L2 取；而且放在 `if ASCEND_IS_AIC` 之前，**MIX 对的两半都付。**

未被否证的窄版：只预读 `gl`/`xs`/`ws`（真正被标量/窄 DMA 读的操作数）且只在 AIV 分支内。

### 点 12 分解 —— 矩阵乘只占 3%，staging 往返才是主体

### 新线：bf16 的 cube 点用的是 int32 staging（4 B/元素）

只有三处 launcher 把 staging 减半：`p1_half_pair::Launch`(4217)、`LaunchMediumScalarHalf`(4795)、
`LaunchActivePacked224`(4916，写作 `/(BF?1u:2u)`)。**那个 `BF?1u:2u` 是关键线索——
半精度 staging 从来只给 fp16 输出用，所有 bf16 输出都走 int32。**
点 12 的 `LaunchAlignedMedium64`(4944) 传的是完整大小。

点 12 的真实流量（M*N = 393,216 个元素）：

| 项 | MB |
| --- | --- |
| **staging 写 + 读（4 B × 2）** | **3.146** |
| weight | 1.049 |
| y | 0.786 |
| x | 0.197 |
| 合计 | **5.178** |

`5.178 MB / 10.47 µs = 494 GB/s`，是 634 GB/s 上限的 **78%**——点 12 接近带宽受限，
而 **staging 占全部流量 61%**，恰好落在那 79% 的固定残差里（三个探针一个都没碰它）。

**换成 fp16 staging 省掉 1.573 MB = 总流量的 30%**，若带宽受限则预测 10.47 → **~7.3 µs**，
即 1.13× → 0.79×，低于 tbest。机制代码已存在（C/D 族的 `DEQF16` + `deqScalar=0x39800000`(2^-12)
配 AIV 侧 `Muls(4096.0f)`），只是从未指向 bf16。

精度论证（待验证）：fp16 相对精度 `2^-11 = 4.9e-4`，而 **bf16 输出自身粒度 `2^-8 = 3.9e-3`，粗 8 倍**，
所以 staging 误差应被最终 bf16 舍入吸收。累加器上界 `K·127²`：点 12（K=256）为 4,129,024、
点 14（K=1023）为 16.5M，经 2^-12 缩放后都在 fp16 范围内，且相对误差与量级无关。

覆盖 bf16 的四个 cube 点：**2、9、12、14**。

### bf16 的半精度 staging —— 两条轴上都被否证

**精度论证完全正确，而这正是它失败的原因。** 最差元素偏差恰是 **1 个 bf16 ULP**
（8.0625 vs 8.000），全部 393,216 个元素无一超过 1 ULP。

但先前把 bf16 的 ULP 说窄了：**8 位有效位 ⇒ 一个 ULP 在二进制区间顶部是 3.9e-3、底部是 7.8e-3**。
所以 `max_rel = 7.8125e-3 = 2^-7` 恰是「干净的 1 ULP 翻转」的签名，不是论证破了。

**杀死它的是评测容差 1e-3 低于 bf16 自身的 eps 3.906e-3 ⇒ 对 bf16 输出，验证器实际要求逐位精确。**

fp16 一侧证明这个阈值是故意设的：

| 点 | 逐位不同 | max_rel | 宽松读法 |
| --- | --- | --- | --- |
| tp1（fp16，现行半 staging） | 1,074,965（**25.6%**） | 9.766e-4 | **0 失败，PASS** |
| tp12（bf16，试验半 staging） | 12,645（3.2%） | 7.8125e-3 | 6,601 失败，FAIL |

**一个 fp16 ULP 最大 9.77e-4，一个 bf16 ULP 最小 3.906e-3；1e-3 正好楔在缝里**——
恰好容纳前者、恰好排除后者，两边都无余量。

所以 `LaunchActivePacked224` 的 `/(BF?1u:2u)` 不是历史偶然，而是**按输出类型锁定的正确性约束，
且已部署在所有合法之处**：点 1/4/15 是仅有的三个 fp16 cube 点，三个都已在用。
点 9/14 是 bf16，同样不可用。**此线彻底关闭。**

### 「字节不是货币」—— 第二次被同一个错误模型误导

| 拿掉的东西 | 字节 | 点 12 的收益 |
| --- | --- | --- |
| 一半 weight DMA | 0.525 MB | **−9.3%** |
| 一半 staging 往返 | 1.573 MB | **−0.4%** |

三倍字节、二十三分之一收益。weight DMA 坐在 AIC 串行链上（B 面板载入 → `LoadDataWithTranspose` → `Mmad`），
cube 卡在它上面；**staging 往返本来就被 4 槽 `CrossCore` 信用环掩盖了**（AIV 排空 tile `i` 时 AIC 在算 `i+1`），
缩小它什么也不缩短。那个 494 GB/s 是记账数字，不是余量。

## 现行模型：每 tile 的工作量

staging 流量被掩盖、K 循环只占点 12 的 2.2% ⇒ 79% 残差是 **AIC 串行链上的每 tile 固定开销**：

```
耗时 ≈ n_tiles × 每tile固定 + 总工作量
```

| 点 | BM×BN×kp | **每 tile MAC 数** | tiles | cube_mac% | 比值 |
| --- | --- | --- | --- | --- | --- |
| 1 | 256×128×768 | **25.2 M** | 128 | **65.6** | 1.04 |
| 4 | 192×128×512 | 12.6 M | 70 | 15.0 | 1.55 |
| 12 | 64×128×256 | **2.1 M** | 64 | 12.2 | 1.13 |

**点 1 是我们最好的点，每 tile 的工作量是点 12 的 12 倍。**

这个模型同时解释了全部否证：点 4 的 BN 越小越慢（128 > 96 > 64，即 7 < 9 < 13 个 tile）、
`p2b32` 把点 2 的 BM 减半后变慢——因为 `n_tiles × F` 随 tile 变小而**增长**。
**更多 tile 从不更好地摊销固定开销，它是把固定开销乘以更多份。**

先前「每核 tile 数越多越好」的框架**符号是反的**，这正是 p2b32 的提交结果与它矛盾的原因。

**杠杆是更少、更大的 tile**，上界由 L0C（`BM*BN*4 ≤ 128 KB`）与 L1（`(BM+2*BN)*kp ≤ 512 KB`）给定。

## 决定性结论：瓶颈是 AIC/AIV 的**重叠**，不是任何引擎的忙时

点 4 的 BM 扫描（BN=128 固定，`judge.sh` 2 轮两遍交错，全部 AC 且误差与基线逐项相同）：

| 变体 | BM | M-tiles | tiles | 耗时 | vs 对照 | **cube_mac%** | **aicore** | **aiv** |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `p4bm192` 对照 | 192 | 10 | 70 | **23.190** | — | 15.0 | 13.84 | 15.58 |
| `p4bm224` | 224 | 10 | **70** | 25.035 | **+8.0%** | 15.3 | 13.54 | 15.43 |
| `p4bm240` | 240 | 9 | 63 | 26.344 | **+13.6%** | 15.3 | 13.33 | 15.41 |
| `p4bm256` | 256 | 9 | 63 | 26.269 | **+13.3%** | 15.8 | 13.05 | 15.20 |

**模型预测的每个指标都如预测般变化，而 kernel 慢了 13%**：`cube_mac` 单调升、`aicore` 单调降、
`aiv` 也单调降——两个引擎都更闲、利用率更高、墙上时间多 3.1 µs。

**这一次测量同时排除了所有「忙时」与「流量」解释。** 时间花在**两个引擎的重叠**上：
tile 变大使流水变粗，4 槽信用环配每核 3.15–3.5 个 tile 时，每个 tile 是更长的不可分步骤，
AIC 能藏在 AIV 后面的部分更少。省 0.8 µs 忙时、赔 3.1 µs 重叠。

这也统一了点 12（那里 `aiv` 升而 `aicore` 降）：**两处 kernel 跟踪的都是重叠，不是忙时。**

**`BM=224` 在 tile 数完全相同（70）下慢 8% ⇒ tile 数根本不是变量。**
原因是 `897 = 4·224 + 1`：专家 0 的最后一条 strip 只有**一行**，却烧掉一整个 strip 的流水步骤。
（这也修正了先前 `TARGETS.md` 把 BM=224 记成「63 tiles / 45% 行利用率」的说法——那是 70 tiles。）

**仪器未颠倒排序**：BM=192 在新旧两个仪器上都胜，向上方向在两边都单调更差。
所以旧仪器把绝对值改了约 26% 但没改次序，**那堆否证不需要整体重验**。

## VDEQF16 —— API 可用，死在数据格式上

`QuantMode_t::VDEQF16` 正是点 4 的 `int32 L0C → half dst` 组合（`quant_processor_fixpipe.h:215` 确认），
调用形式 `Fixpipe<DstT, SrcT, CFG_ROW_MAJOR>(dst, colLocal, quantTensor, params_)` 已从
`copy_cube_out_utils.h:148` 的在树调用点确认，L0C→GM 的 deq-tensor 重载存在，
FB 存 256 个 deq 值、`nSize ≤ 128` ⇒ `nIterNum = 1` 不需分块，L1 余量充足。

**但它要 L1 里的 `uint64_t[n]`——每 8 字节槽一个 fp32。** 把紧排的 `float ws[n]` 展成 8 字节步长，
这台硬件上没有便宜办法：DMA 的目的步长是 **32 字节粒度**（4 字节间隔不可表达）、
向量 `BlkStride` 同样是 32 字节块粒度、`Brcb` 把每个元素铺满整个 32 字节块（步长 32 非 8）、
掩码对源和目的同样生效（`0x5555…` 读的是 `src[2i]` 而非 `src[i]`）、
`Gather` 需要的交错索引本身又是同一个问题下移一层（且撞 H6 雷区）。

只剩标量 `SetValue` 循环：`769 × 8 = 6152` 次存储，单发射约 **3.4 µs**，
而预期节省约 3.8 µs 的 AIV 元素操作——**构造代价约等于优化收益，且落在 AIV 这条要缩短的腿上。**

附带：`SetFixPipeAddr` / `SetFixPipeConfig(eleWise, c0ChStride)` 在 dav_c220 上是
`ASCENDC_REPORT_NOT_SUPPORT`，`cbufWorkspace` 参数是本芯片唯一的供给路径。

附带二：`PrecombinedScale`（已在点 15 启用）**不是**同一个优化——它把 `{MulByRow + Mul}`
换成 `{外积 + Mul}`，而外积本身也是一遍 `nr × nt` 的扫描。两遍变两遍，只是重排不是削减。
这解释了点 15 为何看不出它的收益。

## 确定的机制：点 4 是 AIC MTE2 受限，根因是 weight 行跨距撕裂

`PipeUtilization` 的暖态比值（200 次启动的后半平均，`~/gmm-floor/pipes.sh`）：

| 点 | **AIC mte2** | **AIC scal** | AIC mac | mte1 | fix | AIV vec | scal | mte2 | mte3 | cubeU |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **4** | **77.4%** | 52.5 | 14.7 | 14.7 | 9.3 | 11.3 | 18.1 | 8.0 | 16.0 | 71.4 |
| 1 | 71.7 | 85.3 | **69.1** | 56.9 | 70.1 | 31.9 | 14.8 | 17.9 | 16.9 | 83.0 |
| 2 | 55.9 | **64.5** | 7.0 | 9.0 | 6.0 | 11.8 | 19.6 | 7.1 | 12.4 | 60.2 |
| **12** | 50.0 | **98.9** | 11.8 | 18.3 | 20.2 | 18.4 | 36.5 | 16.7 | 11.1 | 63.0 |

- **点 4：AIC MTE2 77.4%，MAC 仅 14.7%，AIV 各流水全在 19% 以下。** AIV 从来不是瓶颈——
  `aiv_time` 包含它的等待，所以 `aiv > aicore` 造成的「AIV 是长腿」是假象。这也解释了 (b) 为何测出 `s ≈ 0`。
- **点 12：AIC 标量 98.9%（且这是均值，最忙核更饱和）。** 一举解释它全部四个结果——
  唯一动了它的 `halve-w-dma` 正是唯一减少逐行地址运算的探针。
  点 12 的 `srcDValue = 512 ≡ 0 (mod 128)`，**没有撕裂**，所以 pack 对它无用，杠杆必须是「更少的地址运算」。
- **点 1 是验证仪器的对照**：唯一 MAC 达 69.1%、各流水普遍高的点，这就是它 1.04× 的原因。

### 根因的可证推导

`769 = 6·128 + 1 ⇒ 769 ≡ 1 (mod 128)`。weight 第 `r` 行起于字节 `r·769`，其模 128 的余数即 `r mod 128`；
`r` 跑 0..510 时取遍所有余数。而长度 128 的读从余数 `r` 起跨越 `⌊r/128⌋` 到 `⌊(r+127)/128⌋`
两条线，**当且仅当 `r ≢ 0 (mod 128)`**。

⇒ **127/128 的行花 2 次事务、1/128 花 1 次，均值 1.992 次/行**；对齐后恰为 1.000。
⇒ 预测 B 读事务降至 `1/1.992 = 50.2%`。

**实测：AIC MTE2 77.15% → 35.6%（46.1%）**，扣掉 A 约 5% 的事务份额后预期 52.7%，实测略好
（pack 使每行不只对齐还连续）。`L2Cache` 独立佐证：AIC 读事务 **−37%**、命中率 93.0% → **97.8%**。

**所以 `N ≡ 1 (mod 128)` 的相关性原因确定了，而且从来不是尾部 tile。**

### 但 pack 这个载体是亏的（+27%）

pack 读 2.36 MB、写 2.75 MB = **5.11 MB 新增串行流量，超过点 4 全部强制流量 4.46 MB**，
且在 `SyncAll` 前串行执行，落在 AIV MTE2（7.6% → 24.0%）并把两个引擎的均值忙时都抬高
（aic 13.03 → 16.48，aiv 14.31 → 17.94）。净 +5.8 µs：花约 6 µs 省约 4 µs。

**机制对、载体错。** 正在试的替代载体是**整 N 宽的 B 常驻 L1**（不做 pack）：
每行只读一次整行而非被切成 7 片读 7 次 ⇒ 事务降到约 32%（优于 pack 的 46%），
**且 B 字节数减半而非新增 5.11 MB**。L1 放得下：B `512×769 = 394 KB` + A `192×512 = 98 KB` = 492 KB / 512 KB，
代价是 `Prefetch=false`。

## 计数器语义（已查清）

`aicore_time` / `aiv_time` 是**逐核均值**，不是最大值也不是总和。
profiler 源码的公式：`aic_total_cycles / (aic_frequency × ai_core_num × task_duration)`，
两路独立验算（AIC `816559/(20×24.744µs)`、AIV `1724095/(40×26.123µs)`）都得 **1.650 GHz**。

**主频是 1.65 GHz，不是先前几处估算假设的 1.8 GHz（乐观约 9%）。**

**后果**：均值无法界定墙上时间，因为墙由最慢的核决定，而**这个仪器根本不报逐核最大值**。
先前那张「下界」表因此是量纲估算而非约束。

注意：由此推出「最忙核做 1.43 倍均值」是**错的**——`P4WeightedOwnership384` 平衡的是 **weight**
（实测每核 1703.5 全同），不是 tile 数。所以拥有 5 个 tile 的核是 5 个**便宜** tile、总工作量与他人相同，
离散只在每 tile 固定开销上。不均衡项是 `(5 − 3.5) × F = 1.5F`，`F` 未知，远小于 1.43 倍所暗示的量。

## 点 4 的 B 侧已关闭：三个载体，同一个正确机制，全部亏时间

| 载体 | AIC MTE2 | AIC L2 读事务 | 耗时 |
| --- | --- | --- | --- |
| 基线 `p4bm192` | 77.4–77.7% | 81,981 | — |
| `p4pack`（重排 weight） | **35.6%** | −37% | **+27%** |
| `p4fn`（full-N 常驻） | 63.3% | 1.009× | **+11%** |
| `p4span`（owned-span 常驻） | 59.0% | **0.740×** | **+1%** |
| **`p4npf`（只关 `Prefetch`）** | 69.9% | — | **+9%** |

**`p4npf` 这个对照是解读的关键**：单独放弃逐 tile 预取就花 +9%，而宽面板把这 9% 几乎全还回来（+1%）。
所以**宽面板与细粒度预取是同一个约 8% 的替代品，走相反路线**（减少事务 vs 改善重叠），
且**不可合并**——宽面板本身是一次不可分的传输。`p4span2`（`SPANC=3` 双面板乒乓）直接证明了这点：
中位 run 就是 3 个 tile，所以多数 run 仍只持一个面板、没有东西可乒乓，实测与 `p4span` 无异。

**结论：−26% 的 L2 读事务、−18 个百分点的 MTE2 占用，买到整零 ⇒ MTE2 占用不是点 4 的关键路径。**

### 两处我的错（都是简报里的承重假设）

1. L1 里 full-N 实际需要 `Up(769,32)·p.kl = 800·512 = 409,600 B`，不是 394 KB。
2. **常驻是按 `(核, 专家)` 而非按专家。** 实测 25 对、平均 **2.80** 个 tile；专家 0 的 35 个 tile 散在
   **12 个核**上，所以「5 个 M-tile 摊一次载入」从未发生。按 `E[行占用线数] = W/128 + 127/128`，
   整行 769 B 花 7.0 条线、切成七片 128 B 花 12.95 条，**盈亏平衡点是每对 3.0–3.5 个 tile，2.80 在它之下**
   ⇒ B 的 GM 字节数**涨 4 倍到 9.4 MB 而非减半**。我那张「~23,000 事务（32%）」的表前提就是错的。

**可用的产物**：`E[行占用线数] = W/128 + 127/128` 这个事务模型在两个 span 变体上预测误差都在 1.5 个百分点内，
**已验证可用于预判任何 DMA 形状改动**。

### 剩下的读法

每核 MTE2 忙 ~4.0 µs，而逐 tile 节拍 5.2 µs；但砍掉它 26% 的工作毫无变化，而 `mte1` 14.7%、
`mac` 14.7%、`fix` ~10% 全都基本空闲。这读起来像**一条串行的逐 tile 依赖链，其长度是各级延迟之和、
不是任何流水的吞吐**——这能同时解释：占用下降不转化、tile 变大更差（链节更长不可分）、
`p4chunk` 在尾部有效。

**占用度量不了这个。** 正在用分解探针逐级去掉 AIC 链上的一环（Fixpipe / Mmad / LoadDataWithTranspose /
跨核握手），测**节拍**而非占用——这是从未测过的量，与占用是两回事。

## 点 4 的逐 tile 节拍已分解 —— 停止在它上面花时间

逐级删掉 AIC 链上一环的 `GMM_WRONG_ON_PURPOSE` 探针（tiles/core 不变，所以耗时**就是**节拍）。
每个读数都验证了「被删环节的上游流水没有一起塌」，以排除连带效应：

| 探针 | 耗时 | Δ vs 18.13 | 塌掉的 | 上游完好？ |
| --- | --- | --- | --- | --- |
| `w4fix`（无 Fixpipe） | 17.41 | **−0.72（−4.0%）** | fix 10.5 → 0 | — |
| `w4mad`（无 Mmad） | 17.65 | **−0.48（−2.6%）** | mac 14.7 → 0 | mte1 14.1 ✓ |
| `w4ldb`（无 L1→L0B） | 17.86 | **−0.27（−1.5%）** | mte1 14.7 → 5.5 | mte2 79.0 ✓ |
| `w4lda`（无 L1→L0A） | 18.25 | **+0.12（0）** | mte1 → 11.0 | mte2 76.7 ✓ |
| **`w4ring`（无信用环）** | **15.34/15.48** | **−2.79（−15.4%）** | AIC scal 52.8 → 18.3 | 计算全完好 ✓ |

**四个计算环节合计仅 1.47 µs / 18.13 = 8%** ⇒「串行计算延迟链」假设被否，链太短。
Fixpipe、Mmad、L1→L0 载入都动不了这个 kernel，而 **A 侧载入完全免费**。

`w4ring` 定下长腿：脱开握手后 AIV 逐核忙时 **14.47 → 5.94 µs**，AIC 13.35。
**AIV 在成品里纯等待约 8.6 µs，AIC 是长腿。**

### 三个被杀掉的候选解释

- **`w4sr`（owned-span + 无环）16.07 vs `w4ring` 15.48**：span 在删掉环之后**仍亏 3.8%**，
  而它的 MTE2 忙时**短 2.28 µs**（63.7%×16.07 vs 80.9%×15.48）。
  **减少 MTE2 忙时让裸 AIC 流变长** ⇒ 转化失败是描述符固有的，与同步无关。
- **`p4d2`/`p4d3`（2/3 个 B 槽轮转）零收益**，且逐槽 flag 纪律本身花 4%。
  **MTE2 是单个按序引擎——「未完成」意味着排队，不是并行。**（这条退掉了「重叠深度」这个杠杆，不止对点 4。）
- **`p4noack`（只删 ack 半边）完全免费**（18.00 vs 18.02，AIC 标量不变 52.7%）。
  staging 是 `(ceil(m/BM)+e)·nTiles` = **98 个私有槽对 70 个 tile**、按全局 tile id 索引，
  所以 AIC 永不会覆盖未排空的 tile，ack 只约束 flag 队列深度。
  ⇒ `w4ring` 的标量塌陷来自 `CrossCoreSetFlag<2,PIPE_FIX>` 把 AIC 标量卡到自己 Fixpipe 退休，
  加上最后一个 AIC tile 之后的 AIV 尾巴——**两者都是数据依赖本身，不是记账开销。**

### 18.0 µs 的账

| 项 | µs | 依据 |
| --- | --- | --- |
| **MTE2 服务时间** | **~12.5** | 80.9% × 15.48（无环的裸 AIC 流） |

**主导项是 MTE2 的服务时间，而六个载体已证明它对描述符形状（pack / full-N / owned-span / span+无环）、
对齐、重叠深度（`p4npf`/`p4d2`/`p4d3`）、信用环（`p4noack`）全都不变。没有一项是旋钮。**

**五个 cube 点都是 2.3–3.2 µs/tile**，而 BM 跨 64–256、每 tile 工作量跨 2.1M–25.2M MAC。
**点 12 的每 tile 标量成本和点 1 相同，它只是因为 tile 里的工作少 6–12 倍才显得饱和。**

而三分之二的位置已由删除法定下：点 4 上 `w4ring` 让 AIC 标量 52.8 → **18.3%**，而 `p4noack`
（删 ack 与排空、保留 announce）留在 **52.7%** ⇒ 是 `CrossCoreSetFlag<2,PIPE_FIX>` 把标量单元
卡到自己的 Fixpipe 退休。**六个 cube 点跑的是同一个环。**

一处需要保持诚实的张力：点 4 的 BM 扫描把 tile 从 70 降到 63 却亏了 3.1 µs，
所以 **F 不是一个「把 tile 做大就能买回来」的常数**——做大 tile 似乎同时放大 F 或它的暴露。

### 其他两条

- **点 1 的最高流水是 AIC 标量 85.4%，高于它的 mac 68.1%** ⇒ 我们最好的点是**标量受限**，不是 MAC 受限。
  此前「点 1 是唯一吃饱的 cube」是只读 `cube_mac` 得出的，**错**。
- **点 9：fix 65.1% 对 mac 3.6%，18:1**，标量 99.3%。与分数无关（tbest 0.464 不可达），
  但它是表里最畸形的剖面，也是唯一一个 Fixpipe 在几乎不做 MAC 的点上冲到接近最高流水的地方。

### 点 11 的预算重算（旧数字错得比时钟因子更多）

最高流水仅 **42.1%**，没有任何流水饱和——这证实了序列化的说法，但实测 `aiv_time` 让我们能**替换**残差估计而非仅仅缩放：

| 项 | 旧（文档） | 实测/修正 |
| --- | --- | --- |
| 启动地板 | 1.10 | **1.76**（7.09 墙上 − 5.33 核内） |
| `TPipe` 构造/析构 | 0.31 | 已含在 5.33 内 |
| 向量发射 | 0.6–1.0 @1.8GHz | **2.99**（42.1% × 7.09） |
| DMA 传输 | 0.35–0.7 | **1.84**（25.9% × 7.09） |
| 「暴露的串行延迟」 | **4.3–5.0（58–68%）** | **≈2.3（33%）** = 5.33 − 2.99 |

旧的 58–68% 是**重复计数**：用了 1.10 的启动地板（真值 1.76），且 1.8 GHz 的发射估计把向量流水低估了 3–5 倍；
DMA 项也低估 3–5 倍，这与 `h-m-p11XHALF` 的 −0.8% 一致（1.84 µs 忙时 DMA，几乎全部被重叠）。
完美打包下点 11 的地板约 `2.99 + 1.76 = 4.8 µs`，**即 tbest 5.948 在流水受限的地板之上**
⇒ 领先者也让向量流水闲着约 60%。到 tbest 约 1.1 µs，到地板约 2.3 µs。

### 点 13 是剩下最大的、已量化的靶子（且不碰描述符）

AIV mte2 **71.0%** 是全 15 点里最高的 AIV 占用，16.90 of 19.87 µs 是逐核忙时
⇒ **搬运引擎有 29% 的墙上时间是闲的**。成因已记录在本文档（`BalancedOverlapShortGroupMatmul`
只有一对 `xraw_`/`wraw_`，所以第 *i+1* 块的 DMA 必须等第 *i* 块的前导 `Cast` 对
加一个完整的 `PipeBarrier<PIPE_V>` 排空）。

按恒定服务率：71% → 100% 给出 `19.87 × 0.71 = 14.1 µs`，而向量流水的 46.5%（9.24 µs 工作量）
**装得进这 14.1 里，所以重叠是可行的而不只是算术**。换到判题口径是 23.47 → 约 16.7，而 tbest 17.617。

### 三个不变量

1. **MTE2 忙时在九种配置里都是 13.90–14.94 µs（±3.6%）**，跨 kc ∈ {32,64,128}、nb ∈ {96,192,288}、
   一或两个 raw 缓冲、srcStride 0 或 65。即每核 103 KB @ 7.3 GB/s，**对「字节是怎么被请求的」不变**。
   ⇒ **事务模型第三次被否，且是更强形式：服务时间本身对形状不变。**
2. **`aiv_time / dur` = 86.2 ± 0.4%** 跨全部九种。耗时就是逐核 AIV 周期 ÷ 0.862；
   那 14% 是 40-block 的 ramp 与收尾，**从不移动**。
   九种配置在块数、缓冲数、描述符形状上都不同而它仍不动 ⇒ 它**不是** per-chunk 也不是 per-descriptor，
   而是 per-**core** 或 per-**kernel**。
3. **提高占用总是比它收回的多花向量工作。** kc 128→64→32 把 vec 忙时推到 9.12→10.63→14.17 µs
   （每把块数翻倍约 +1.5 µs 向量工作）。`h-m-p13b` 是唯一真推动了占用的（+3.5pp），
   代价 vec +7.6pp、scal +11.7pp，净 −0.7%。**旋钮在两个方向上都已到最优。**

### 但它蕴含的地板不是好消息

完美重叠给出 `14.5 / 0.862 = 16.8 µs` 应用级，按点 13 实测的 judge/app = 1.19 换算是
**约 20.0 µs 判题口径——而 tbest 是 17.617，比我们完美重叠的地板还低 12%。**

⇒ **点 13 不像点 4 那样「关闭」。有人在打败一个我们用这个算法到不了的地板，所以差距是结构性的。**
唯一能定价的结构替代是 cube 路径，而它死在 F 上：63 个单 token 专家 × 2 个 N-tile = 126 tile / 20 核
= 6.3 tile/核，按 F ≈ 2.7 µs/tile 是**在任何 MAC 之前就有约 17 µs 的 AIC 标量**。
正确判词：**对调参关闭，结构上开放且未解释。**

## 点 12：announce 已确认是最大的结构性成本，但两种重排都收不到它

| | 耗时 | AIC scal | mte2 | mac | mte1 | fix | aic | **aiv** |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `h-m-p11Q` | 7.27 | **98.9** | 50.4 | 11.5 | 17.8 | 19.6 | 4.63 | 5.24 |
| `w12ring` | **5.88（−19.1%）** | **38.1–39.6** | 56.4 | 11.8 | 18.0 | 20.0 | 4.58 | **3.63** |

**环占点 12 的 98.9 个标量点里的 60 个、占墙上时间的 −19.1%**（点 4：34 点、−15.4%）。
每 tile 是 1.4–1.8 µs 的阻塞，**两个 body 上都如此** ⇒ `F ≈ 2.3–3.2 µs/tile` 的大部分现已有归属，
且**六个 cube 点共享**。

| | 耗时 | AIC scal | aiv | 判词 |
| --- | --- | --- | --- | --- |
| 基线 | 7.27 | 98.9 | 5.24 | — |
| `p12noack`（只删 ack） | 7.26 | 99.0 | 5.23 | **恰好 0**，同 `p4noack` |
| `p12pair`（每 2 个 tile 才 announce） | 7.59 | **81.7（−17pp）** | 5.55 | **+4.4%，更差** |

- **重排 1「先排下一个 B 再 announce」本来就在出货代码里**：第 *t+1* 个 tile 的 B 描述符在
  `kernel.asc:1818`（`CubeFullKBody`）和 `:3909`（`…ScalarHalf`）就已排队——在 k 循环、Fixpipe 和 announce 之前。
  阻塞期间 MTE2 一直在忙下一次载入，**没有东西可挪**。
- **重排 2 亏**：它确实把阻塞减半（scal −17pp），但让 AIV 等成对把它的启动推迟一个 tile、尾巴变长。

**而 `aiv` 这一列改写了整个环的结论**：`w12ring` 省下的是 **1.61 µs 的 AIV 等待自旋**（5.24 → 3.63），
而 AIC 几乎不动（4.63 → 4.58）。点 12 的耗时 = `AIC 流 + AIV 最后一个 tile + ramp` ≈ 4.6 + 0.56 + 1.5 ≈ 7.3 ✓。
⇒ **环的成本不是可删的 AIC 开销，它就是 AIV 在等数据，即依赖本身**，这正是为什么把 announce 减半
只能把成本挪动而不能移除。它也回溯解释了 `halve-w-dma` 的 −9.3%：缩短 AIC 流会提前最后一次 announce，
从而提前 AIV 的尾巴。

⇒ 点 12 的杠杆是 **AIC 流的长度**（MTE2 50% = 3.6 µs，在 1.05 MB 强制 weight 流量上）
或**更便宜的 AIV 最后一个 tile**，不是环，也不是描述符重塑（不变量 1 第三次禁止了它）。

## 待决：285 GB/s 是逐核还是聚合？

两个点的服务率从不同的引擎数落到同一个数字：

| 点 | 搬运者 | 字节 | MTE2 忙时 | 聚合 |
| --- | --- | --- | --- | --- |
| 13 | 40 AIV | 4.13 MB | 14.5 µs | **285 GB/s** |
| 12 | 20 AIC | 1.05 MB | 3.68 µs | **285 GB/s** |

两种读法，**对点 13 给出相反判词**：

- **逐核上限**（约 7.1 GB/s 每 AIV、约 14.2 每 AIC，乘积相同是巧合）⇒ 点 13 的 40 个 AIV
  让 20 个 AIC 的 MTE2 引擎**完全闲置**，一个把专家分给 cube 核去载入的 MIX 核能把可用带宽**翻倍**。
  M=1 时 cube 的 MAC 阵列约 94% 空闲——平时这就否决了它，但**在带宽受限的点上，
  一个 MAC 闲而 MTE2 忙的引擎正是你想要的**。这能解释 tbest 为何在我们的 AIV-only 地板之下。
- **聚合墙**约 285 GB/s（HBM 或 NoC）⇒ AIC 加不了东西，点 13 的传输地板就是 **14.5 µs**，
  而 tbest 17.617 判题 ≈ 14.8 µs 应用级意味着领先者在**约 100% DMA 占用、几乎没有 ramp** 下跑。
  那么奖品根本不是重叠，而是不变量 (2) 说「从不移动」的那 **14% ramp/收尾**。

**一次 block 数扫描（40/30/20/10）就能定论**：聚合 GB/s 随块数下降则是逐核上限，保持约 285 则是聚合墙。
正在测。

## 285 GB/s 已定论：既不是聚合墙也不是逐核常数，而是一个 9.1 µs 的逐核截距

weight 字节固定 63 × 255 × 257 = 4,128,705 B。两种归一化都报：

| blocks | 每核字节 | 耗时 | **聚合 GB/s**（按耗时） | **逐核 GB/s**（按耗时） | AIV mte2 | mte2 忙时 µs |
| --- | --- | --- | --- | --- | --- | --- |
| **40** | 103.2 KB | 20.06 | **206** | **5.15** | 73.1 | 14.66 |
| 30 | 137.6 KB | 22.69 | 182 | 6.07 | 76.6 | 17.38 |
| 20 | 206.4 KB | 28.63 | 144 | 7.21 | 80.0 | 22.90 |
| 10 | 412.9 KB | 49.76 | **83** | **8.30** | 83.7 | 41.65 |

**两个假设都不成立。** 聚合随块数下降（282 → 99 GB/s）⇒ **没有 285 GB/s 的墙**；
但逐核**反而上升**（7.04 → 9.91 GB/s）⇒ **也不是逐核常数**。两个 285 的吻合纯属巧合。

（判词用的是「按耗时」两列，因为它们不需要 profiler 归一化；
`ai_core_num` 在比值公式里是「启动的块数」还是「物理 40」未能确定，所以「按忙时」列带这个保留。两种读法判词相同。）

### 在正交轴上交叉验证后得到的模型

`h-m-p13HALF`（weight DMA 减半，40 blocks）= **13.73 µs，不是 10.03** ⇒ 减半字节只省 6.33 µs，不是省一半时钟。
五个点、两条轴、一条线：

**`dur ≈ 9.1 µs + 0.715 µs × 每核工作单元`**，残差 ±0.86 µs 跨 13.7–49.8 µs。

| 构型 | 每核单元 | 预测 | 实测 |
| --- | --- | --- | --- |
| 40 blk，½ 字节 | 7.09 | 14.14 | 13.73 |
| 40 blk | 14.175 | 19.20 | 20.06 |
| 30 blk | 18.9 | 22.58 | 22.69 |
| 20 blk | 28.35 | 29.33 | 28.63 |
| 10 blk | 56.7 | 49.59 | 49.76 |

**块数轴与字节数轴各自独立地落在同一个截距上**，这是它可信的原因（单独一条轴能被六七个模型拟合）。
**在 40 blocks 时这 9.1 µs 是点 13 的 45%。**

### 这 9.1 µs 不是什么

- **不是启动或 ramp。** `aiv_time/dur` 在扫描中是 0.855 / 0.866 / 0.885 / 0.903。
  若这 9.1 µs 落在所有核的周期之外，该比值在 40 blocks 时必须是 **0.56**。
  ⇒ **核在这段时间里是忙的，它是逐核的工作。**
- **不是 groupList 扫描。** `kernel.asc:1405` 已经用**一次** `DataCopyPad` 把整个列表拉进 UB、
  只有一个 `Barrier<MTE2_S>`，之后所有 `GetValue` 都是 UB 本地的。点 11 的类比在这里不成立。
- **不是 per-Row 碎片**：解 40-block 与 10-block 两个方程得出每次 `Row()` 调用 9.9 µs，
  对一个 20 µs 的核来说数值上荒谬。
- **尚未定位。** 可见的逐核无条件工作（两次小 DMA、一个 MTE2→S barrier、UB 视图构造、
  ≤128 次迭代的专家定位循环）定价约 **3 µs，不是 9**。
  9.1 µs @ 1.65 GHz ≈ **15,000 周期逐核**，其中约 10,000 周期无归属。
  这个 family 没有分解探针（`PRIORITY.md` 已记录 `halve-k` 不覆盖它），需要新建一个。

### MIX 搬运工的想法在架构上本就无效（与哪个分支赢无关）

**AIC 的 MTE2 只能 GM → L1/L0。** 这块芯片上 AIC→AIV 只有两条路：
GM 中转往返（即点 4 占 42% 流量的那个成本，其唯一载体 `p4pack` 实测 +27%），
或在真做了一次 cube op 之后走 L0C → UB。**所以 AIC 核当不了纯搬运工**，
只能在 cube 里算自己那份专家——而那又直接落回 `F`：63 个单 token 专家 ≥63 tile / 20 核 = 3.15 tile/核，
按 F ≈ 2.3–3.2 µs/tile 是**在任何 MAC 之前约 8.5 µs 的 AIC 标量**，而只换来一小部分字节。

而扫描独立地说方向本来就反了：**逐核效率随每核字节减少而下降**，
所以把同样的 4.13 MB 摊到 60 个搬运者而不是 40 个，会让每个搬运者都处在更差的速率上
——按实测趋势外推到 69 KB/核是约 4.3 GB/s × 60 = 258 GB/s，对今天的 282 是打平偏亏，而代价是一次 MIX 重写。

**⇒ 点 13 唯一的具体线索现在是那个未定位的 9.1 µs 逐核项，不是带宽。**

## 修正：上一节那个 9.1 µs 截距，约 3 µs 是拟合假象

把扫描里每条流水单独拟合，**然后用字节轴交叉验证**（上次救了我们的那一步）：

| blocks | 每核单元 | 耗时 | **scal µs** | vec µs | mte2 µs |
| --- | --- | --- | --- | --- | --- |
| 40 | 14.18 | 20.50 | **5.12** | 9.19 | 14.99 |
| 30 | 18.90 | 22.69 | **5.04** | 12.00 | 17.38 |
| 20 | 28.35 | 28.63 | **5.73** | 17.49 | 22.90 |
| 10 | 56.70 | 49.76 | **8.71** | 34.04 | 41.65 |
| 40，½K（`p13HALF`） | 7.09 | 13.73 | **4.52** | 5.04 | 8.35 |

| 流水 | 固定 µs | 每单元 µs | 在 7.09 单元处预测 | 实测 | 判词 |
| --- | --- | --- | --- | --- | --- |
| vec | 0.94 | 0.584 | 5.08 | 5.04 | **纯边际** |
| **scal** | **3.50** | 0.090 | 4.14 | 4.52 | **73% 固定——截距在这里** |
| mte2 | 5.52 | 0.634 | 10.01 | **8.35** | **假象——两轴不一致** |
| 耗时 | 9.72 | 0.700 | 14.68 | 13.73 | — |

**MTE2 那个「5.5 µs 固定部分」是拟合假象**，而两轴的不一致本身就是发现：
**逐核 DMA 速率随每核流长单调上升**——51.6 KB/核 6.18 GB/s、103 → 6.89、138 → 7.92、206 → 9.01、413 → 9.91。
五个点、8 倍跨度、**未饱和**。线性拟合把这个凹性报成了截距；**不存在那个量级的固定 MTE2 成本。**

### 修正后的分解

| 成分 | µs | 依据 |
| --- | --- | --- |
| 固定标量 | 3.7 | 两条轴一致 |
| — 其中专家定位走查 | 0.9 | `w13scan` |
| — **未定位的固定标量** | **2.8** | 残差 |
| xScale 前导 DMA | 1.0 | `w13xs` |
| 固定 vec | 0.9 | 两条轴一致 |
| MTE2 速率曲线凹性 | ~3 | 两轴不一致，**不是固定成本** |

**⇒ 未解释的量是约 2.8 µs，不是 9.1。上一节「45% 的点未解释」是错的。**

### 两个探针的结果

- **`w13scan`（删掉全部专家定位标量工作）：scal 忙时 5.12 → 4.19 ⇒ 走查是 0.93 µs，不是 3.7。
  我押的首要嫌疑被否。**
- **`w13xs`（删掉 252 字节的 xScale 前导 DMA，保留 group-list DMA 及其 barrier）：
  19.13 vs 20.27，−5.6%。** mte2 忙时 14.72 → 13.72，scal 不变。
  一个微小描述符在共享的 `Barrier<MTE2_S>` 前花掉约 **1 µs 的暴露冷往返**，占截距 11%，且不在标量流水里。
- **TPipe 不用探：按代码即死。** 点 13 实例化 `Static = true`，所以 `P13Pipe` 是 `EmptyResource`
  （`kernel.asc:1573,1650`）——这里根本没有 TPipe 可删。点 11 的 0.31 µs 在这里不存在。

### 那 1 µs 收不到

重排无用：两个前导 DMA 共享同一个 `Barrier<MTE2_S>`，把 xScale 沉到第一次 weight 发射之下需要
**第二个** MTE2_S barrier，而本文档已给它定价（点 11 的 C3，退休要等整个未完成 MTE2 队列，+4.6%）。
改用预热：`p13pre`（`Init` 里 4 + 16 个 `DataCachePreload`，15/15 AC）**20.85/21.28 vs 20.03/20.17，+4.9%，否决**。
二十个串行标量发射的 preload 比它要藏的冷延迟更贵——与 cube body 上「五个就已经有害」记录的是同一机制。

### 地址局部性争用：2.7 倍（长期警告）

`w13scan` 的混淆本身是发现：强制 `expert = 0` 让 40 个核去流**同一个 65 KB 区域**而非 63 个不同区域，
字节数、描述符形状、向量工作全部相同，而 **MTE2 忙时 14.72 → 39.96 µs（2.7×）**、耗时 20.27 → 44.6。
纯粹的地址局部性争用。**而上面那条逐核速率曲线实际上就是它——是并发/局部性曲线，不是流长曲线。**
⇒ 对任何「让多核共享一个 weight 面板」的设计，这是一条长期警告。

## 点 11 的阶段分解：成本在 `WholeReduceSum` 这个原语上，不在归约这个概念上

基线 `h-m-p11Q`：耗时 **7.38**，vec 41.9%、scal 36.5%、mte2 26.0%、mte3 2.8%，aiv 5.36。

### 但原因不是「归约」，而是那个原语

按满 lane 宽度（64 int16/周期、32 fp32/周期、1.65 GHz、`nr = 26`、`pairs = 400`、`realPairs = 385`）定价：

| 阶段 | 元素操作 | 预测 vec µs | 实测 Δvec | 比 |
| --- | --- | --- | --- | --- |
| split | 31,200 int16 | 0.30 | 0.28 | **1.0×** |
| mul | 26,624 int16 | 0.25 | 0.44 | 1.8× |
| cast + add | 31,200 fp32 | 0.59 | 0.53 | **0.9×** |
| **reduce** | 10,192 fp32 | **0.19** | **1.36** | **7.2×** |

**五个阶段里四个跑在接近满 lane 宽度。只有归约离峰值 7 倍**，而它搬的数据是所有阶段里最少的。
⇒ 成本在 `WholeReduceSum` **原语**上，不在归约**概念**上。

### 因此转置方案不需要

把 token 装进 lane 要拿 1.36 µs 的归约去换：一次 26×800 int8 的 UB 内转置（若可表达约 0.2–0.4 µs）
**加上**一个每次只有 26 lane 宽的 769 次 FMA 内循环，还要求 x 是 k-major（而 x 是 token-major 来的）。

**更便宜的动作不碰布局**：把两级 `WholeReduceSum` 换成**逐对的满宽 `Add` 树**
（385 → 192 → 96 → 48 → 24 → 12 → 6 → 3 → 2 → 1，约九个 `repeat = nr` 的 `Add`），
读约 20,000 个 fp32、按 32/周期 ≈ **0.38 µs 对 1.36**。同样数据、同样布局、不需要 gather。
预测约 1 µs = 这个点的 13%。**而且它大概顺带带走 `Gather`/`CreateVecIndex`**，
因为逐对树的结果可落在连续位置——即 C4 想要的效果，却不需要 C4 那个落在 H6 雷区的 `dstRepStride` 技巧。

### 两条要撤回的

- **那些 barrier 是免费的。** 本文档此前记的「30 条向量指令对 19 次硬同步」是怀疑而非测量；
  删掉批循环里全部十个 `PipeBarrier<PIPE_V>` 值 **−0.7%，在噪声内。该说法作废。**
- **「向量流水离峰值约 15 倍」是错的。** 那个算法数的是 79 万 MAC，而这个核真正的向量负载是
  **每核约 120,000 个元素操作**——int8 操作数在任何乘法之前要被拆分、加宽、折叠，**MAC 只占 23%**。
  按元素操作算只离峰值 **2.3 倍**，且那 2.3 倍全部是那一个归约阶段。
  **与事务模型是同一种错误形状：问题的自然单位不是硬件收费的单位。**（这是本项目第三次为此付费。）

## 那个「标量地板」可能根本不是地板

上一轮的 `w11bar` 只删了十个 `PipeBarrier<PIPE_V>`，而**每个 batch 的四个 `GvBarrier<>` 从未被测**。
而 `GvBarrier` 就是 `SetFlag<E>(0); WaitFlag<E>(0)`（`kernel.asc:760`）
⇒ **`GvBarrier<MTE2_V>` 恰好就是「标量单元被阻塞，直到那 20 KB 的 x DMA 落地」。**

若 `w11gv` 证实，则结论比探针本身大得多：**那 2.7–3.7 µs 不是可删的工作，而是被 profiler
记在标量列里的暴露 DMA 延迟**。可删工作与暴露等待需要相反的修法，而我们在两个 body 上都在找错的那一个。

**它还与已测的东西汇合**：`w13xs` 发现那个 252 字节的 xScale 前导 DMA
花掉约 **1 µs 的暴露冷往返，位置就在共享的 `Barrier<MTE2_S>` 之前**——
那是另一个 body 上的同一机制，当时没有把两者联系起来。
若证实，类级别的陈述变成「**AIV-only 的 body 要付 2.7–3.7 µs 的暴露 DMA 延迟，记在标量流水上**」，
杠杆是**重叠深度**而不是更少的指令。

一个要留在视野里的反证：点 13 上二十个 preload 花 **+4.9%**（`p13pre`），
而点 11 上 `p11Q` 的五个是 −4.7% 那个胜利的一部分
⇒ **这类 body 上的延迟隐藏已被测为符号不定**，所以探针无论显示什么，载体问题仍然开放。

## 点 13 的前导探针必须用合成 group list

Agent 正确地在建之前标记了问题：点 13 的 group list **驱动控制流**

## 重要修正：上一节「`WholeReduceSum` 是原语级发现」基本是错的——真正的变量是**跨步**

在动手移植之前用算术否掉了它，没花 NPU 时间：

- **点 11 的 reduce 源是跨步的**：`srcRepStride = pairs/8 = 50` 个 block
  ——读 64 个 float，然后跳 400。
- **点 7/8 的是连续的**：`srcRepStride = 8` 个 block，恰好就是那个 64 元素窗口。`RowDot` 也是连续的。
- 决定性的数字不需要测量：点 7/8 的 reduce 读 `8192 + 128 = 8320` 个 fp32，
  **按满 lane 宽度是 0.16 µs**，而它们**整个** AIV vec 忙时是 **1.05 µs**（52.0% × 2.02）。
  一个 7 倍的 reduce 会是 1.1 µs——**装不进总量里。**

**⇒ 源连续时那个原语不可能离峰值 7 倍，所以点 11 那 7.2× 基本上是跨步造成的。
可复用的发现是关于「跨步向量读」的，不是关于 `WholeReduceSum` 的。
`p11add` 的胜利应重读为：折叠之所以有效，是因为它把跨步读换成了连续读，不是因为 `Add` 打败了 `WholeReduceSum`。**

所以对点 7/8 正确的第一步是探针而不是移植：`w78red`（删掉两级 reduce、保留 barrier）一次构建就能定出天花板。
已脚本化、已做基线校验，容器关机前没来得及建。若它显示约 0.16 µs，则折叠在点 7、点 8 和 `RowDot` 上
**都移植不出任何东西**。

## 点 11 的 block 扫描：那个固定标量是**逐核**的，与每核 batch 数无关

| blocks | 每核 batch | 耗时 | **scal µs** | vec µs | aiv |
| --- | --- | --- | --- | --- | --- |
| 40 | 1 | 8.07 | **3.11** | 3.40 | 5.33 |
| 20 | 2 | 9.03 | **2.13** | 5.60 | 7.02 |
| 10 | 4 | 14.43 | **2.22** | 9.67 | 12.74 |
| 5 | 7 | 24.87 | **2.79** | 17.53 | 23.48 |

标量停在 **2.1–3.1 µs**，而每核 batch 数走 1 → 7、vec 忙时走 3.40 → 17.53（5.1×）。
**逐 batch 的成本会缩放约 7 倍。** 它也不是 per-kernel 的，因为在每个核数下都存在。
**⇒ 分母是「核」。记为这个核类别的一条已测性质，原因未知**（八个删除探针都没动它）。

耗时随块数下降**单调上升** ⇒ 块数越少严格越差，**点 11 是并行度受限的**。

### 顺带解决了 `ai_core_num` 的歧义（点 13 的保留可以摘掉）

若 profiler 的比值除的是固定的 40，则在工作量相同而核数降 8 倍时，
总 AIV 周期（`aiv × freq × core_num`）会**上升** 4.4 倍。而按「启动的块数」算它们是**下降**的：
352k → 232k → 210k → 194k——这正是「核数更少、每核各付一份固定成本」该有的样子。
**⇒ `ai_core_num` 是启动的块数，逐核数字是「每个活跃核」。点 13 那些带保留的逐核数字得到验证，保留摘掉。**

## 点 7/8 的跨核拆分：已定价，阻塞点不是性能

现状 `blocks = min(2·availableCoreNum, N)` 在 `N = 2` 时是 **2 个 block，40 个核闲 38 个**；
aiv 忙时 1.41 µs / 耗时 2.02 µs。

- **上限**：拆 8 份时逐核向量工作从约 1,216 周期降到约 152，省约 0.9 µs。
  但 2.02 里有 0.61 µs 是启动/ramp 且不可分，所以最好情况约 **1.1 µs ≈ −45%**，
  两个点各约 +8 分，合计约 **+1.1 总分**。
- **`SetAtomicAdd` 累加进 y**：需要在任何核累加之前把 y 清零。规则 2.12 禁止第二次 kernel 启动，
  所以清零必须在同一个 kernel 内——而那需要「清零」与「累加」之间有一个设备级屏障，
  否则早到的核的贡献会被晚到的核的清零擦掉。单次 AIV-only 启动里没有这种屏障。**按此写法是死的。**
- **GM 中转往返**：部分和极小（S=8 时 64 字节），所以**和 `p4pack` 的数 MB 完全不是一回事，成本不在流量**。
  它需要做最终求和的核知道其余 S−1 个核已完成，而 `CrossCoreSetFlag`/`WaitFlag` 是 AIC↔AIV 的，不是 AIV↔AIV。

### 规则读法（我的读法，非定论）

把 rules.md 的条文逐条对上：**没有一条禁止单次启动内的跨 block 同步。**
2.5 是硬编码/按数据规律跳算、2.6 是写标记跳过计算、2.7 是**利用**旧输出或未初始化内存**跳过计算**、
2.10 是空核/识别预热/把计算移出计时、2.12 是一次计算用多次 kernel。
AIV↔AIV 的协调发生在单次启动之内、不跳过任何计算、不碰判题与计时——按条文读是允许的。

**真正的阻塞是工程问题，有两个：**
1. **死锁**：自旋要求相关 block 同时驻留。40 个 block 对 40 个核时成立，但调度器不保证共驻。
2. **flag 本身的初始化**：手写 flag 需要一块已清零的 GM，而清零又回到 2.12
   ——垃圾值可能恰好匹配哨兵值。这一条比死锁更难绕。

**⇒ 因此第一件要查的不是规则而是 API**：Ascend C 的 `AscendC::SyncAll()` 正是设备级 block 屏障，
由框架实现并管理其 flag 内存。`grep` 显示当前 kernel 里**没有** `SyncAll`、也没有任何原子操作，
所以它在这个工具链里是否可用是个未答的问题，需要容器。若可用，则两个工程阻塞同时消失，
而且用的是有文档的 API 而不是手写自旋。

## R 扫描结果：每核 batch 数是**纯成本**，overlap 永远赚不回来（点 11，2026-11-09）

`mkp11r.sh` 的 R 扫描在 **40 blocks 固定不变**的前提下把每核 batch 数从 1 推到 4，
所以它没有 block 扫描的 core-count 混淆。三个变体都 15/15 PASS，点 11 bit-exact
（`max_rel = max_abs = 0`）。串行三轮，WARM 中位数（µs）：

| 变体 | R | batches/core | r1 | r2 | r3 | 均值 | 相对 R=32 | first6avg 均值 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `p11add` | 32 | 1 | 6.540 | 6.580 | 6.540 | **6.553** | — | 8.852 |
| `p11r16` | 16 | 2 | 7.060 | 7.380 | 7.020 | **7.153** | **+9.2%** | 9.358 |
| `p11r8`  | 8  | 4 | 8.230 | 8.310 | 8.150 | **8.230** | **+25.6%** | 10.555 |

两个口径（WARM 与 first6avg）同向、单调、无交叠，三轮内部散布 ≤0.36 µs，远小于效应。

**被证伪的是 `mkp11r.sh` 自己写在注释里的那个假设**：R=32 时 38/40 的 block 只跑一个
batch，所以 `GvBarrier<MTE2_V>` 没有「下一个 batch」可重叠；R=16 给了它一个，
`w11gv` 定位的 0.56 µs 暴露头尾本应被吃掉。实测相反——多一个 batch 不是赚 0.56 µs，
而是**净亏**：

- 1 → 2 batches：+0.60 µs（一个额外 batch）
- 2 → 4 batches：+1.08 µs（两个额外 batch，即 +0.54 µs/个）

即**每核每多一个 batch 固定付 ~0.57 µs**，极其一致。这个固定成本比它所能解锁的
全部重叠（0.56 µs 的暴露头尾，且只有第一个 batch 的头和最后一个的尾是暴露的）还大，
所以**无论 R 取多少都不可能转正**——不是「R=16 不够好、试试 R=24」，是这条路的符号错了。

**与点 13 的 kc 扫描同形**：那边 128→64→32 把 vector busy 从 9.12 推到 14.17，
也是「切得更碎以换重叠」而净亏。两次独立 body、两次同向，所以这是这台机器上的
一个一般性质，不是点 11 的局部怪事：**切分粒度的固定成本在这个尺度上压过它买到的
并行度**。它也顺手解释了点 13 为什么有那么陡的逐核曲线——点 13 本身就是高
batches-per-core 的那一端。

**结论：弃。** `p11r16`/`p11r8` 两个变体废弃，R=32（一核一 batch）保持。连带关闭
「给 barrier 造一个可重叠对象」这整条线，而不只是关闭 R=32 这一个取值。

| --- | --- | --- | --- | --- |

**八次全部 2.020，末位都不动，而且 `w78red` 在点 7/8 上仍然 bit-exact**
（只有点 11 按预期 FAIL，898 个元素超容差）。删掉代码既不改时间也不改答案，
只有一个解释：**那段代码在点 7/8 上根本没执行。**

查实了：`WholeReduceSum` 在整个 emit 里只有 6 处，分属三个 body，无重复副本。
点 7/8 走的不是 `IntegerProductLongNarrowDot`，而是
`longdot_capacity::Launch` → `SearchLongDotCapacity11840033<Capacity,BF,Scalar>`
或 `SearchLongDotCapacityDMAScales`（fp + scale 地址未 4 字节对齐时），都是
`<<<2,nullptr,stream>>>`。**blk=2 对得上，所以之前是靠 block 数认错了 body**：
`IntegerProductLongNarrowDot` 的守卫（`M==1 && N<=2`，`blocks=min(2*cores,N)`）
也会给出 2，两条路长得一样。

**修正 TARGETS.md 此前的记载**：`IntegerProductLongNarrowDot` 不服务点 7/8，
它和 `RowDot` 一样是**15 个点都到不了的死码**。全表现在有两个死 body，不是一个。

**这条线彻底关掉，但不是因为"收益约 0.16 µs"。** 读 `longdot_capacity::Dot::Run`
发现它的归约**已经就是 Add 对折树**：

```
Add(integerSums, integerSums[64], integerSums, 64, ...)   // 带 repeat 的那一级
Add(integerSums, integerSums, integerSums[32], 32)
Add(integerSums, integerSums, integerSums[16], 16)
Add(integerSums, integerSums, integerSums[8],   8)
→ Sum<0>(): for(i<8) total += values.GetValue(i)          // 最后 8 个走标量
```

也就是说 `p11add` 想往点 7/8 搬的那棵树，**点 7/8 已经有了**，而且尾部 8 个元素
是标量 `GetValue` 而非向量原语。所以：
- 预测"≈0.16 µs ≈ 零"**数值上对了，机制上错了**——不是"折叠省不下来"，是**没有可折叠的对象**。
- 前一节"真正的变量是跨步（srcRepStride）"仍然成立且更有分量：点 11 是唯一一个
  用跨步 `WholeReduceSum` 的 body，而它已经被 `p11add` 修掉了。这个原语级发现
  **没有第二个点可搬**，`RowDot` 的那份保险也没有意义（它是死码）。

**结论：弃，并且连带注销"把 fold 搬到 `RowDot` 作为 11/14 新点的保险"这项**——
往死码里写保险不是保险。真要给新点上保险，得先知道新点会不会命中
`longdot_capacity`，而那条路上的对折树已经在了。

## AIV↔AIV 同步：载具存在，但一个 barrier 比整个点还贵（2026-11-09）

剩下的是 DMA 进出（点 5 的 contract body 用 `DataCopyPad` 过 UB，点 6 的 unrolled 不过）、
groupList 扫描、标量 encode/store 链，以及已被判定为「人人都付」的启动地板。

**点 5 与点 6 的那个不对称值得记**：同样 5 个预取，点 5 值 0.103 µs 而点 6 值 0。
点 6 的 E=1，`if(e>1u)` 直接跳掉 groupList 预取，它**没有依赖 groupList 的地址链**；
点 5 的 E=5 有。所以预取的价值不跟着输入大小走，跟着**是否存在一条
groupList→地址的依赖链**走。这是下一刀该瞄的地方，而不是预取本身。

## 点 11 的累积阶段分解：账算平了，而且硬地板是 2.62 µs（2026-11-09）

上一轮的七个单删探针加起来是 3.12 µs / 7.38，但在最高流水只有 42% 的点上，单删会互相藏。
`mkp11lad.sh`（容器 `~/gmm-rebuild/`）是**累积**阶梯：从 `p11add` 一路删到只剩
`TPipe` + 14 个 `LocalTensor` 声明。同会话串行、`judge.sh` 5 reps、每一级都用
`opdur.sh` 的 op name 确认仍然是 `SearchN1FixedLayoutSafe7100000` 跑 40 个 block
（这一条是硬要求：探针的 0 结果必须先排除「那行没被执行」）。

| 级 | 内容 | µs | 相邻 Δ |
| --- | --- | --- | --- |
| `p11add` | 基线 | **7.060** | — |
| `lad6` | 全部向量工作删除（split/mul/cast/add/fold/reduce/尾部 4 条） | 5.380 | **−1.68** |
| `lad7` | 再删 x 与 scales 的 DMA（投机的和循环里的）＋ `MTE2_V` | 4.060 | **−1.32** |
| `lad10` | 再删 weight 通路、专家扫描、5 条 `DataCachePreload`、序章向量 | 3.920 | −0.14 |
| `lad11` | 只剩 `TPipe` + 14 个 UB 声明 | **2.620** | −1.30 |
| `h-nop` 40 blk | 空核，40 个 block | **2.300** | −0.32 |

于是账**正好**算平：

| 项 | µs | 占 7.06 | 依据 |
| --- | --- | --- | --- |
| 40-block 启动地板 | **2.30** | 33% | 空核，5 reps，2.26–2.34 |
| `TPipe` 构造/析构 + 14 个 UB 声明 | 0.32 | 5% | `lad11 − nop` |
| 标量序章（两个 64 位整除） | 1.30 | 18% | `lad14 − lad15`；**但在完整 body 里是零**，见下 |
| x + scales 的 DMA | 1.32 | 19% | `lad6 − lad7` |
| 全部向量工作 | 1.68 | 24% | `p11add − lad6` |
| weight 通路 + 专家扫描 + 预取 + 循环 + 52 B 存储 + 两个 `GvBarrier` | 0.14 | 2% | `lad7 − lad10`；`lad12`/`lad13` 各删一半都不动 |

### 更正：40 block 的启动地板是 2.30，不是 1.10

旧表（本文件「点 11 的真实时间去向」）记的是 1.10 µs / 15%。实测 **2.30 µs / 33%**，
高一倍多。而且它随 block 数几乎线性：

| blocks | 40 | 26 | 20 | 13 | 10 | 4 | 1 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 空核 µs | 2.30 | 1.64 | 1.40 | 1.14 | 1.02 | 0.68 | 0.62 |

拟合 **≈ 0.58 + 0.043 × blocks**（每个 block 约 43 ns）。这条曲线对所有点都可用，
而且它解掉了 block sweep 的「core 数混淆」——启动那一项现在可以直接减掉。

### 两个被证伪的杠杆

**1. 那两个 64 位整除：阶梯底部值 1.30 µs，完整 body 里值 0。**
`begin=uint64_t(s.m)*GetBlockIdx()/cores` 这个切工作的写法在 `kernel.asc` 里出现 **14 处**，
看起来像那个一直缺的「到处都有效」的杠杆。实测不是：

* `p11div`（去掉白付的 `uint64_t` 转换——`M≤32768`、`cores≤40`，乘积最大 131 万，
  32 位足够）：15/15 逐位一致，**7.180 对 7.260，−0.08，噪声内**。贵的是除法本身不是宽度。
* `p11shift`（`>>5` 代替 `/cores`）：7.680，**更慢**——但这个仪器无效，`/32` 和 `/40`
  给出不同的行划分，改了工作量。正是 `w13scan`/`p4pack` 那类混淆。
* `p11recip`（`n/40 == (n*0xCCCCCCCD)>>37`，对所有 `uint32_t` 精确相等，划分逐位不变）：
  15/15 逐位一致，**7.480 对 7.460，平局**。

⇒ 除法在底部是关键路径，在完整 body 里躲在影子里。**阶梯的内部归因不能上移**，
只有它的地板是可以上移的。这一条对以后所有累积阶梯都成立。

**2. 减少 block 数：预测 −0.33，实测 +1.54。**
启动地板 40→20 省 0.90，而 R sweep 说每核每多一个 batch 付 0.57 ⇒ 预测 −0.33。实测相反：

| 变体 | tp11 µs |
| --- | --- |
| `h-m-p11Q` 40 blk | 8.020 |
| `p11add` 40 blk | **7.140** |
| `p11blk20` 20 blk | 10.220 |
| `p11a20` = `p11add` + 20 blk（15/15 逐位一致） | 8.680 |

我把 0.57 用错了轴：R sweep 是**固定 40 block 改 R**，每核行数不变；减 block 会让
每核行数从 26 翻到 51，于是把 3.0 µs 的每核工作也翻倍。**40 个 block 已经是最优**，
而且这一点是结构性的——点 11 的并行度本来就不够（每核 26 行），启动地板是这份
并行度的价钱，换不掉。

### 定价：结构上还剩多少

* **谁也删不掉的硬地板 = 2.62 µs**（启动 2.30 + `TPipe`/声明 0.32）＝ 37%。
* tbest 5.948 减掉硬地板还剩 **3.33 µs**；我们是 7.06 − 2.62 = **4.44 µs**。
  ⇒ **要在这块区域里再省 25% 才能打平 tbest。**
* 这 4.44 里可寻址的是：向量 1.68、DMA 1.32、标量序章 1.30（在影子里）、其余 0.14。

逐块定价：

| 块 | µs | 还能拿多少 | 为什么 |
| --- | --- | --- | --- |
| 向量 | 1.68 | **0.3–0.5** | `p11add` 已经把 7.2× 的那个离群值（`WholeReduceSum`）吃掉了；单删表里剩下的 split 0.21 / mul 0.26 / cast+add 0.58 都在满 lane 宽度的 0.9–1.8× 之间，没有离群值了 |
| x DMA | 1.32 | **0（当前结构下）** | 不是带宽（`h-m-p11XHALF` 把字节减半只 −0.8%），所以是延迟/发射。要藏它必须有第二个 batch，而拿到第二个 batch 的唯一办法是减 block，代价 +1.54 |
| 标量序章 | 1.30 | **0** | `p11recip` 逐位一致、平局 |
| 启动 | 2.30 | **0** | 并行度不够，换不掉 |

**⇒ 需要 −1.11 µs 才能打平 tbest，手上够得着的是 −0.3 到 −0.5。这个 body 到不了 tbest 5.948。**
tbest 只比我们实测的全删地板（3.92）高 2.03 µs，所以领先者要么在可寻址部分比我们
高效 1.55×，要么走的是一条根本更便宜的每行通路——**不是把这个 body 再调一遍能到的**。

## 启动地板是硬件的,不是我们 binary 的——而点 11 的瓶颈是重叠,不是工作量(2026-11-09)

### 一、地板:谁都在付

问题不是「地板是硬件的还是我们的」,而是「**2.30 µs 是不是只有我们在付**」。
配对实测,答案是**不是只有我们**:

`ladnop<B>` = 我们那份完整 binary(5401 行,`.text` 866 KB,文件 1.60 MB),把点 11 的
kernel 体换成**立刻 return**——没有 `TPipe`、没有声明、什么都不做,和 `h-nop` 的 `Nop`
干完全一样的活(零)。`h-nop` 是 82 行、`.text` 230 KB、文件 411 KB。同一个 `judge.sh`
(300 iters / 60 warmup)、同一个 case、全程串行、**每个 block 数前后脚配对**,好让机器漂移
在差值里相消。脚本 `~/gmm-rebuild/mkladnop.sh` 与 `~/gmm-floor/floorab.sh`。

| blocks | `h-nop`(411 KB) | `ladnop`(1.60 MB) | Δ |
| --- | --- | --- | --- |
| 1 | 0.620 | 0.640 | +0.02 |
| 2 | 0.660 | 0.660 | 0.00 |
| 16 | 1.220 | 1.220 | 0.00 |
| 20 | 1.420 | 1.420 | 0.00 |
| 40 | 2.260 | 2.300 | +0.04 |

`msprof` 的量化步长就是 0.020,五个点各自 5 reps 的散布是 ±0.04~0.07。
**`.text` 大 3.8 倍、文件大 3.9 倍,地板一点没动。** ⇒ 地板是 launch/runtime 的硬成本,
**裁 binary 一分钱都省不下来**(生成器将来瘦身也不会换来时间),而且**领先者按同样的
block 数付同样的钱**。

于是我自己之前那条撤回(「启动地板/binary 体积」实验)**结论成立,但理由要换**:
当时的理由是「点 7/8 的 tbest 2.069 高于我们的在核忙时 1.41,所以领先者付同样的地板」,
这个数是错的——用实测的 2-block 地板 0.66 重算,我们可寻址部分 1.52、他们 1.30,
是实打实的 1.17× 差距,不是「他们等于我们的全长」。真正让撤回成立的是上面这张配对表。

### 二、地板是「并行度」的价目表:点 11 在 4.12 µs 预算下只能长什么样

tbest 真值约 **4.124 µs(判题器)= 3.898 µs(容器,因子 1.058)**。x 全量 = 1027×769 = **771 KB**。
每核 DMA 速率由实测定标:20 KB / 1.32 µs = **15.1 GB/s**。

| blocks | 每核行数 | 启动地板 | 单核 x DMA | 工作量×行数比 | 总计 | 地板+DMA 下界 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 1027 | 0.62 | 49.9 | 175.4 | 176.3 | 50.5 **已超** |
| 4 | 257 | 0.75 | 12.5 | 43.9 | 45.0 | 13.2 **已超** |
| 10 | 103 | 1.01 | 4.99 | 17.6 | 18.9 | 6.00 **已超** |
| 13 | 79 | 1.14 | 3.84 | 13.5 | 15.0 | 4.98 **已超** |
| 20 | 52 | 1.44 | 2.49 | 8.88 | 10.6 | 3.93 **已超** |
| 26 | 40 | 1.70 | 1.92 | 6.83 | 8.85 | 3.62 占预算 93% |
| 34 | 31 | 2.04 | 1.47 | 5.29 | 7.66 | **3.51 最小** |
| 40 | 26 | 2.30 | 1.25 | 4.44 | 7.06 | 3.55 占预算 91% |

**结论和原来的猜想相反:减 block 不是没划算,是灾难性地不可能。** x 的 771 KB 必须过一次
HBM,少核就没有足够的 MTE2 并行度去搬它——20 block 时「地板 + 把 x 搬完」就已经 3.93,
超过 3.898 的全部预算。可行区间只有 **26–40,最优 34**。
所以 2.30 µs 不是「选 40 block 的冤枉钱」,是**唯一可行的并行度区间的入场费,人人都付**。

### 三、真正的缺口是重叠,不是工作量——上一轮我把这个点结案是错的

`min(启动地板 + 搬完 x) = 3.509 µs`,而 tbest 容器值 **3.898**。
**⇒ tbest 只给全部算术留了 0.389 µs。领先者的算术是几乎完全藏在 x 流后面的。**

我们在 40 block 的两个极值:

| | µs |
| --- | --- |
| 实测(完全串行):2.28 地板 + 0.32 `TPipe`/声明 + 1.30 标量 + 1.32 DMA + 1.68 向量 + 0.14 | **7.04** |
| 同样的工作量,完美重叠:2.28 + 0.32 + max(1.30, 1.32, 1.68) | **4.28** |
| tbest | **3.898** |

上一轮我写的是「要 −1.11,够得着 −0.3~−0.5,这个 body 到不了 tbest」。那个算式把四项工作
当成既不可压缩**又必须串行**的。**串行这一半是错的:可拿的是 2.76 µs,不是 0.5。**
完美重叠仍比 tbest 差 10%,但那是「差一成」,不是「差一倍」。**这个点不该关闭。**

### 四、那 0.39 µs 里塞不进什么,以及为什么现有的重叠载具都失败

要藏的是 1.30 标量 + 1.68 向量 + 0.14 = **3.12 µs,需要藏掉 ≥87%,现在藏了 0%**。
两个已测的载具都输了,而且原因同一个:

* **减 R 做批次重叠**:R=32→16→8 是 6.553 / 7.153 / 8.230,每核每多一个 batch 固定付
  ~0.57 µs(expert 扫描、weight 通路、栅栏都要重跑),比能藏的 min(DMA,向量)/2 还大。
* **批内双缓冲**:UB 没有空间。`static_assert(UB_BYTES==184672u && UB_BYTES<=188160u)`
  ——**188 KB 里只剩 3,488 B**。x 的一块缓冲是 R*C=25,600 B,再要一块就得先腾出 25.6 KB,
  而占地最大的是两块 fp32 中间量(`f` 和 `other`,各 R*C*2 = 51,200 B)。

⇒ **下一个该瞄的不是「再调这个 body」,而是「把 fp32 中间量减半以腾出 x 的第二块缓冲」**:
`other` 的存在只为在 Add 之前放 odd 半边,`p11add` 之后它仍被 Cast 需要。
这是一条 UB 预算驱动的、可做可测的改动,而且它是上面唯一还没被证伪的重叠载具。

### 候选新 body:把专家沿 N 打包走 cube —— 下界 8.9 µs,死在两项上(2026-11-09)

点 11 是 E=4, M=1027, K=769, **N=1**。cube 的 N 粒度是 16,所以 N=1 补到 16 和 N=4 补到 16
同价:把 4 个专家的权重列沿 N 拼成 N=4,对全部 1027 行一次算完,再按 groupList 选列,
那 4× 的多余 MAC 确实是**免费**的。这个想法本身没问题。纯算术下界:

cube 速率不用规格书,用**我们自己的点 1** 定标:E4 M4096 K768 N1024 在 20 AIC 上 26.889 µs,
3.221e9 MAC ⇒ **1.198e8 MAC/µs = 3630 MAC/cycle/AIC**,即 16×16×16=4096 架构峰值的 **89%**。

| 项 | 量 | µs | 判断 |
| --- | --- | --- | --- |
| 1. cube MAC | 1027×769×16 = 1.264e7 | **0.106** | 可忽略(粗估 ~0.1 对了) |
| 2. x 流入 | 789,763 B 必须过一次 HBM | **2.615** | **单项已超预算** |
| 3. L0C→UB | 1040×16 int32 = 66,560 B(仅 1027 有用) | ~0.05–0.1 | 可忽略 |
| 4. AIV 尾部 | 1027 次反量化 + bf16 cast + 2,054 B 存储 | ~0.01–0.05 | 可忽略 |
| 5. `F`(每 tile AIC 标量) | ≥2 tile × 2.3 | **≥4.6** | **单项 = 预算的 118%** |
| | | **合计 ≥ 8.89** | vs tbest **3.898**,vs 现有 AIV body **7.06** |

**两项各自单独就超预算,而且原因互不相干:**

**(2) 搬 x 的引擎数砍了一半。** AIC MTE2 只到 GM→L1/L0,AIC 到 AIV 只有 GM 往返或
(真做了 cube 之后的)L0C→UB —— 所以 cube 路线搬 x 只能用 **20 个 AIC MTE2**,
而现有 AIV 路线用的是 **40 个**。现有路线实测 40×15.1 = 606 GB/s 聚合 ⇒ 1.303 µs;
同样的每引擎速率给 20 个引擎就是 **2.615 µs**,加 20-block 启动地板 1.42 = **4.035**,
已经超过 3.898 的全部预算,而 MAC 还没开始。
(**留一个口子**:这里假设 AIC MTE2 的每引擎速率等于 AIV 实测的 15.1 GB/s。AIC 读 GM→L1
用更宽的事务,可能更快;若 20 个 AIC 能摸到 606 GB/s,这一项就回到 1.30 µs 并且**能过**。
这是可测的,不是可争的。但它救不了这条路,因为——)

**(5) `F` 独自就是预算的 118%。** 每 tile 的 AIC 标量成本 2.3–3.2 µs 是在五个 cube 点上
测出来的,其中三分之二是 `CrossCoreSetFlag<2,PIPE_FIX>` 卡在自己的 Fixpipe 后面。
tile 数压不到 1:单个 tile 要装下整个 A 需要 **789,763 B 的 L1,而 L1 只有 524,288 B**,
所以**至少 2 个 tile**,F ≥ 4.6 µs。tile 数是被 L1 容量按死的,不是调参能压的。

⇒ **这条路不建。** 它不是「差一点」,是比我们现在的 7.06 还慢,而且慢在两个结构性原因上。
点 11 的出路仍然是上一节那条:**腾 UB 做 x 的第二块缓冲,把 3.12 µs 的工作藏进 1.30 µs 的
x 流后面**(完美重叠 4.28,tbest 3.898,差一成)。

### 顺带:p10 的 K=1 不同构

打包之所以免费,是因为 **N 是输出轴**,多算的列直接丢掉。
p10(E=4, M=1025, **K=1**, N=769)的退化在 **K,也就是归约轴**上:沿 K 拼专家会把它们加到
一起,结果是错的,不是多余的。K=1 能做的只是零填到 32(同样免费),得 M=1025, K=32, N=769
= 2.52e7 MAC ≈ 0.19 µs —— 但 p10 的输入只有 1,025 B(x)和 3,076 B(weight),
**它的地板在输出**:y 是 1025×769×2 = **1.58 MB**,比 p11 的整个输入还大 2 倍。
所以 p10 要算的是写出带宽的下界,和 p11 完全不同的一道题。它只差 −19.6%。
